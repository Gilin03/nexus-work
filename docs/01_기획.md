# NEXUS WORK — 앱·DB 하드닝 설계서 (역할 A)

작성일: 2026-10-17 · 담당: 홍주형(역할 A) · 상태: 설계 초안 (코드 구현 전)

## 1. 목적과 범위

- **목적:** 팀 프로젝트 NEXUS WORK(사내 업무 포털 + AI Agent 방어전)의 **웹 앱·DB 기반을 완전히 방어된 상태로** 만든다. 의도적 취약점은 만들지 않는다(2026-10-17 사용자 결정). 앱은 끝까지 완전 방어 상태로 둔다.
- **담당 범위(역할표):** 게시판 코드 방어(입력 검증, 쿼리 파라미터화, 업로드·인증 제한), 관리자 경로 보호, DB 최소권한. 도구: Flask, MySQL.
- **추가 확정 범위(2026-10-17):** AI 챗봇의 **화면과 엔드포인트**, 게시판 + **자유게시판**. 챗봇 응답 생성·Tool 호출 로직은 타 담당이다.
- **범위 밖(타 담당):** 챗봇 응답 생성·Tool 호출, Security Gateway, 보안 대시보드(D), n8n 연동 관리 API(D), Wazuh/Graylog/n8n 연동 설정. 단, 이들이 붙을 **접점**(앱 이벤트 로그 출력 — 형식은 C와 협의, 기밀 문서용 DB 계정)은 이 설계에서 제공한다. Wazuh·Graylog 설정과 탐지 룰은 C, 자동 대응은 D, 방화벽 연동은 B 담당이다.

### 1-1. 기능 범위 (2026-10-17 확정: 일반 회사 ERP + 그룹웨어 + NEXUS WORK)

NEXUS WORK는 **그룹웨어 + ERP 업무 시스템 위에 AI Agent 방어전을 얹은 포털**이다. 범위가 넓으므로 단계로 나눠 필수 단계를 먼저 완성한다. 화면은 목록·상세·간단한 입력 위주로 두고 복잡한 업무 규칙은 만들지 않는다.

| 구분 | 모듈 | 데이터·기능 | 민감도 | 단계 |
|---|---|---|---|---|
| 그룹웨어 | 로그인·권한 | employee/manager/admin | - | **필수** |
| 그룹웨어 | 문서함 | 일반 문서, 기밀 문서(M&A 계획 등) | 기밀 분리 | **필수** |
| 그룹웨어 | 주소록(직원 검색 포함) | 사내 직원(이름·부서·직책·내선), 공유·개인 연락처 | 일반 | **필수** |
| 그룹웨어 | 게시판 | 공지·글, 첨부 | 일반 | **필수** |
| 그룹웨어 | 자유게시판 | 자유 글(첨부는 게시판과 같은 업로드 규칙) | 일반 | **필수** |
| 그룹웨어 | AI 챗봇 화면·엔드포인트 | 대화 입력, 응답 표시, 대화 기록 | 본인 대화만 | **필수** |
| 그룹웨어 | 전자결재 | 결재 상신·승인·반려 | 본인·결재선만 | **필수** |
| 그룹웨어 | 일정, 메일 | 화면 위주 | 본인 | 확장 |
| ERP | 인사 | 직원 정보(일반), 급여(기밀) | 급여=기밀 | **필수** |
| ERP | 경비 | 경비 신청, 결재 연동 | 본인·팀 | **필수** |
| ERP | 재무 | 월 손익 보고(기밀) | 기밀 | **필수** |
| ERP | 구매·발주, 고객·영업 | 발주서, 거래처, 고객 목록 | 일반~팀 | 확장 |
| 관리자 | 사용자·권한 관리 | 역할 변경, 잠금 해제 | 관리자 | **필수** |
| 방어 | 챗봇 응답 생성·Tool 호출, Security Gateway, 보안 대시보드(D), n8n 관리 API(D), 탐지·대응 | 타 담당 | - | 팀 |

접근 규칙(서버에서 강제): 직원=본인 데이터, 매니저=팀 데이터, 관리자=전체, 기밀=별도 DB 계정과 별도 권한 확인.

**ERP 모듈 범위 제한(확정):** 인사·급여, 경비, 재무는 **시드 데이터(미리 넣어 둔 예시 데이터) + 목록·상세 화면까지만** 구현한다. 급여 계산, 경비 정산, 회계 처리 같은 복잡한 업무 규칙은 만들지 않는다. 접근 통제(본인·팀·기밀)는 이 범위에서도 그대로 적용한다.

## 3. 아키텍처

```
브라우저 → Flask 앱 ──(nexus_app 계정)──→ MySQL: users, employees, documents, posts, attachments, chat_messages
nexus-messenger(Flutter) ─┤             ├─(토큰 인증, /api/v1/*)→ MySQL: api_tokens, conversations,
  데스크톱+모바일          │                                      conversation_members, messenger_messages
              │
              ├─(nexus_conf 계정, 기밀 권한 확인 후에만)→ MySQL: confidential_documents
              ├─ 업로드 파일 → instance/uploads (웹루트 밖, 무작위 이름)
              ├─ 실시간 메시지 → Socket.IO(같은 포트, app/realtime.py)
              └─ 보안 로그 → logs/security.jsonl (JSON Lines, Wazuh 수집 대상)
```

- 앱 구성: `config` · `db` · `validators` · `security`(로그·CSRF·헤더·제한) · `uploads` — **S2 완료**. `auth`(로그인·로그아웃·세션·잠금·비밀번호 변경·`login_required`/`role_required`) — **S3 완료**. `portal`(문서함·기밀 문서함·직원 검색·게시판·자유게시판·첨부) — **S4 완료**. `erp`(급여·재무 보고·경비)·`approvals`(전자결재) — **S5 완료**. `admin`(사용자 목록·역할 변경·잠금 해제) — **S6 완료**. `chat`(챗봇 화면·엔드포인트) — **S7 완료**.
- 챗봇 동작(S7, 구현·검증됨, H16): 로그인·CSRF 필수, 메시지 1~2,000자와 제어문자 검증, 사용자당 분당 20회 제한, **대화 기록은 본인 것만**(팀장·관리자도 본인 것만) 저장·조회, 폼으로 사용자·화자를 바꿀 수 없다. **응답은 신뢰하지 않는다:** 글자로만 취급해 이스케이프하고(HTML·`javascript:` 해석 안 함), 제어문자 제거와 8,000자 제한을 거치며, 응답기 예외는 가두어 내부 정보 없이 안내 문구만 보인다. 사용자 메시지는 응답을 기다리기 전에 먼저 확정한다. 보안 로그에는 대화 내용 대신 글자 수만 남긴다(내용은 `chat_messages`에만 있다).
- **다른 담당과의 접점(응답기):** 실제 AI 응답과 Tool 호출은 다른 담당 몫이며 `app.config["CHAT_RESPONDER"]`를 `responder(user, message, history) -> str`로 교체해 연결한다(기본값은 시험 응답). `user`는 지금 로그인한 사용자이고, **챗봇의 권한은 이 사용자의 권한을 넘을 수 없다**(Tool 호출마다 Security Gateway가 사용자·역할·자원 권한을 다시 검사). `history`는 본인의 최근 10건이다. 응답기는 자체 시간 제한을 둬야 한다.
- 관리자 동작(S6, 구현·검증됨): `/admin/*`은 블루프린트 단위로 role=admin을 서버에서 검사하고(비로그인은 로그인 화면, 그 외는 403), 변경은 POST+CSRF만 허용한다(H9). 역할 변경은 즉시 반영되며(사용자·역할은 요청마다 DB 재조회), **본인 역할은 바꿀 수 없다**(그래서 관리자가 0명이 되지 않는다). 역할 값은 허용목록(employee/manager/admin)만 받고, 화면을 연 뒤 다른 곳에서 바뀐 사용자는 덮어쓰지 않는다(409). 강등되어 팀장·관리자 권한을 잃은 사람은 결재선에 이미 지정되어 있어도 결재를 처리할 수 없다(`approver_role_revoked`). 잠금 해제는 실패 횟수와 잠금 시각을 함께 초기화한다. 모든 변경과 거부는 `admin_action` 이벤트로 남고, 비밀번호 해시는 화면에 내보내지 않는다. 앱 DB 계정은 `users`에서 로그인 처리·역할 변경에 필요한 4개 열만 수정할 수 있다. 사용자 등록·비밀번호 초기화·수동 잠금은 2026-10-19에 더했다(아래 "시스템 관리"). 삭제는 이력 보존을 위해 두지 않았다. 자동 잠금·회수는 D의 n8n 담당.
- ERP·결재 동작(S5, 구현·검증됨): 접근 범위는 직원=본인, 팀장=같은 부서, 관리자=전체이며 서버에서 강제한다(H14). 급여·재무는 기밀 DB 계정으로만 읽고 재무 보고는 manager·admin만 본다. 경비는 항상 임시저장으로 시작해 소유자 본인만 제출할 수 있다.
- **결재선(상신자가 결정):** 상신자가 팀장·관리자 중 최대 5명을 **순서대로** 고른다(경비 제출과 일반 결재 상신 모두). 본인·중복·일반 직원은 지정할 수 없고(앱 검사, 본인은 DB 트리거도 거부), 잘못된 선택이면 400으로 되돌아가며 경비 상태는 바뀌지 않는다.
- **순차 결재:** 첫 결재자만 `pending`, 나머지는 `waiting`. 지금 차례인 결재자만 승인·반려할 수 있고(차례 전 결재자는 403 `not_your_turn`, 결재선에 없는 사람은 관리자라도 403), 승인하면 다음 결재자에게 차례가 넘어가며, 마지막 승인이 나면 문서와 연결 경비가 승인된다.
- **반려:** 사유(1~500자)가 필수이며 어느 단계에서든 반려하면 문서와 경비가 반려되고 남은 단계는 `skipped`가 된다. 반려된 경비는 종결 상태다(재상신 불가).
- **철회:** 상신자 본인만, 첫 결재자가 처리하기 전(진행 중이고 1단계)에만 가능하다. 철회하면 문서는 `withdrawn`, 단계는 `skipped`, 연결 경비는 임시저장으로 돌아가 고쳐서 다시 상신할 수 있다. 첫 결재 뒤·종결 후에는 409.
- 종결 상태(승인·반려·철회)는 바꿀 수 없고(H15), 승인과 철회가 동시에 오면 문서 행 잠금으로 한쪽만 성공한다.
- 포털 동작(S4, 구현·검증됨): 기밀 문서는 manager·admin만 열람하고 기밀 DB 계정으로만 조회한다. 공지 쓰기는 manager·admin만, 자유게시판은 로그인한 모두가 쓴다. 글 삭제는 작성자 또는 admin만. 첨부는 **형식·개수·용량 제한이 없고**(2026-10-19 사용자 결정, 아래 "첨부 제한 해제"), 서버가 만든 uuid 이름으로 `instance/uploads`에만 저장하고 항상 다운로드로만 내려준다. 직원 검색의 LIKE 와일드카드는 문자 그대로 취급한다. **첨부 미리보기(2026-10-19):** 글 화면은 그림(png·jpg) 첨부를 `<img>`로 바로 보여 주고 PDF는 "보기"(새 탭)와 "다운로드" 링크를 둔다. 글쓰기 화면은 내용 칸에 그림·PDF를 붙여넣거나 끌어다 놓으면 첨부 칸에 넣고 미리 보여 준다(`app/static/paste-attach.js`, 같은 출처 스크립트라 CSP `script-src 'self'` 유지, 파일은 하나만). 미리보기 경로 `/attachments/<id>/view`는 로그인 필수이며 업로드 때 검증된 png·jpg·pdf만 인라인으로 내리고(txt는 404, 다운로드만), 응답에 경로 전용 CSP(이미지 `default-src 'none'; sandbox`, PDF `default-src 'none'`)와 nosniff·`X-Frame-Options: DENY`·CORP를 붙인다. 그래서 전역 CSP 설정은 응답이 이미 정한 CSP를 덮어쓰지 않게 바꿨다(`setdefault`). 서버 검증(확장자·내용·2MB)은 그대로이고 브라우저 쪽 검사는 안내용이다. 업로드 파일 자체는 여전히 서버가 올리는 순간만 검사한다(바이러스·악성 PDF 내용 검사는 하지 않음).
- **전자결재 확장(2026-10-19):** 기존의 순차 결재선·승인·반려·철회·경비 연동은 그대로 두고 실제 업무에서 쓰는 기능을 더했다. 구현은 `app/approvals.py`.

  - **근태:** 시각은 서버가 한국 시간(UTC+9)으로 정하고 사용자가 보낸 날짜·시각은 쓰지 않는다. 같은 날 두 번째 출근은 `INSERT IGNORE`의 0행으로 409(동시 요청에도 한 번만), 퇴근은 `check_out IS NULL`일 때만 UPDATE. 09:01 이후 출근은 지각으로 표시(색과 글자 둘 다).
  - **휴가:** 평일만 일수에 넣고(주말 제외), 반차는 하루만 0.5일, 병가는 연차를 차감하지 않는다. 연차·반차는 승인된 것과 **대기 중인 것까지** 미리 차감해 잔여를 계산하고 부족하면 409. 대기·승인된 기간과 겹치면 409(취소·반려한 기간은 다시 신청 가능). 같은 사용자의 신청은 사용자 행 `FOR UPDATE`로 한 줄 세워 잔여·중복 검사와 입력 사이에 다른 신청이 끼지 못하게 했다. 승인·반려는 같은 부서 팀장 또는 관리자만, **본인 신청은 누구든(관리자도) 본인이 결재할 수 없고**(앱 + DB CHECK), 대기 중일 때만 가능하며 조건부 UPDATE로 동시 처리 시 한쪽만 성공한다. 반려는 사유 필수. 취소는 신청자 본인만, 대기 중일 때만. 처리마다 `hr_*` 이벤트가 남는다.
  - **입력 검증:** 종류는 허용목록, 날짜는 `YYYY-MM-DD` 형식과 실제 날짜, 시작일은 오늘 기준 30일 전~365일 후, 사유 1~200자(제어문자 불가), 월 조회는 `YYYY-MM`. 폼에 `status`·`decided_by`·`user_id`·`days`를 실어 보내도 무시한다.
  - **제외한 것(범위 밖):** 인사 정보 수정·입퇴사 처리, 평가, 초과근무·급여 연동, 공휴일 달력(공휴일도 평일로 센다), 근태 정정 요청, 부서 이동 이력. 연차 부여는 일률 15일이며 근속에 따른 가산은 없다.
- **첨부 제한 해제(2026-10-19, 사용자 요청: "첨부파일은 개수·용량·파일 제한을 두지 말자"):** 게시판 글과 전자결재(상신·결재 처리)의 첨부는 형식·개수·용량을 제한하지 않는다. 원래는 홍주형(역할 A)의 방어 과제(A2, "위험한 파일명을 넣어도 거부되거나 무해하게 처리됨")였던 부분이라, **"거부"에서 "받되 무해하게 처리"로** 방어 방식을 바꾼 것이다. 구현은 `app/uploads.py`의 `save_attachment`.
  - **무해하게 처리하는 방법:** (1) 서버가 만든 무작위 이름(확장자 없음)으로 웹루트 밖 `instance/uploads/`에만 저장하고, 원래 이름은 DB의 표시용 문자열일 뿐 경로에 쓰이지 않는다. (2) 표시 이름은 경로를 버리고 안전한 문자(영문·숫자·한글·`._- `)만 남기며 점으로 시작하는 숨김 이름은 막는다(120자까지, 확장자 유지). (3) 형식은 거부하지 않고 **분류만** 한다: 그림(png·jpg)·PDF는 확장자와 내용(매직바이트)이 맞을 때만 그 형식, txt는 text/plain, 나머지(php·exe·html·svg·확장자 없음 포함)는 모두 `application/octet-stream`. (4) 내려줄 때는 항상 첨부(다운로드)+nosniff이고, 인라인 미리보기는 (3)에서 분류된 그림·PDF만 한다(미리보기 응답에는 전용 CSP). (5) 파일을 1MB 조각으로 디스크에 직접 써서 큰 파일이 서버 메모리를 차지하지 않고, 크기·SHA-256은 쓰면서 계산한다. (6) 저장 도중 실패하면 쓰다 만 파일과 이미 쓴 파일을 지우고 요청 전체가 롤백된다. (7) 운영체제가 열지 못하는 파일(백신 격리 등)은 500이 아니라 404로 답하고 `attachment_unreadable`로 기록한다.
  - **한도 해제 방식:** 첨부를 받는 요청(`portal.post_new`, `approvals.approval_new`, `approvals.approval_decide`)만 본문 상한을 푼다(`security.apply_upload_limit`). Flask는 `max_content_length=None`을 "설정값(2MB)을 쓴다"로 해석하므로 사실상 무한대 값으로 푼다. 첨부가 없는 나머지 요청(로그인 등)과 **프로필 사진은 2MB 상한이 그대로**다. 필요하면 `.env`의 `MAX_UPLOAD_BYTES`로 첨부 요청에 상한을 다시 걸 수 있다(비우면 제한 없음). 글자 칸 크기(500KB)와 한 요청의 폼 항목 수(1000개)는 프레임워크 기본 보호를 유지한다(그래서 한 요청에 올릴 수 있는 파일은 사실상 1000개 안쪽이다). 게시판 글쓰기도 파일 여러 개를 받는다. 파일 크기 열은 4GB를 넘는 파일을 위해 `BIGINT`로 넓혔다.
  - **위험(제한을 풀면서 생기는 것):** 디스크 용량이 사실상 유일한 한도라서 로그인한 누구나(공방전에서는 탈취한 계정 포함) 큰 파일을 반복 업로드해 디스크를 채울 수 있다. 다른 팀이 올린 악성 파일이 서버 디스크에 그대로 남는다(실행되지는 않지만 백신이 격리·경보를 낼 수 있다). 업로드 건수·용량을 탐지하는 규칙은 아직 없다(Graylog에서 `post_created`의 `attachments`·`bytes`와 `approval_created`의 `files`를 볼 수 있다). 위험이 현실이 되면 `MAX_UPLOAD_BYTES`로 한 번에 상한을 걸 수 있다.
- **프로필 사진(2026-10-19):** 상단바 아바타(누르면 `/account/photo`)에서 본인 사진을 올리고 바꾸고 지운다. 사진이 없으면 이름 첫 글자를 보여 준다. png·jpg만, 확장자와 내용(매직바이트)이 모두 맞아야 하고 크기는 앱 업로드 상한(2MB)이다. 표 `profile_photos`(사용자당 한 행, `nexus_app`에는 SELECT·INSERT·DELETE만 — 바꿀 때는 지우고 다시 넣어 UPDATE 권한이 없다), 파일은 웹루트 밖 `instance/uploads/avatars/`에 무작위 이름으로 둔다. 올리고 지우는 대상은 항상 로그인한 본인이며 폼에 다른 `user_id`를 실어도 무시한다. 보는 경로 `/users/<id>/photo`는 로그인한 모두에게 열려 있고(상단바·추후 목록용) 이미지로만 열리도록 DB에 저장한 형식·nosniff·`default-src 'none'; sandbox` CSP·CORP를 붙인다. 이미지를 다시 인코딩하지는 않는다(내용 검사는 형식·크기까지). 미리보기 스크립트는 같은 출처 외부 파일이라 CSP를 그대로 지킨다.
- 인증 동작(S3, 구현·검증됨): 로그인 실패 메시지는 원인과 무관하게 동일, 5회 실패 시 15분 잠금(잠긴 동안은 맞는 비밀번호도 거부), 로그인 성공 시 세션·CSRF 토큰 재발급, 유휴 30분·절대 8시간 만료, 사용자·역할·잠금은 요청마다 DB 재조회. 세션은 서명된 쿠키지만 `users.session_version`과 맞아야 유효하다. 로그아웃·비밀번호 변경은 이 값을 올려 이전 쿠키(다른 기기 포함)를 모두 무효로 만든다(S8). 기기별 개별 폐기는 서버 측 세션 표가 필요해 하지 않았다.
- 점검·로그(S8): 비로그인으로 열리는 화면은 `/login`·`/healthz`뿐이며 테스트가 라우트 목록 전수로 확인한다. 의심 입력(SQL 인젝션·XSS·경로 탐색 형태)은 차단하지 않고 `suspicious_input` 이벤트로 기록해 탐지(C)가 쓰게 한다. 실행은 `python run.py`(서버 버전 비노출, 기본 루프백. `.env`의 `APP_HOST`·`APP_PORT`로 바꾸고 명령줄 값이 우선하며, 루프백이 아닌 주소인데 시드 비밀번호가 공개된 예시 값이면 기동 때 경고)이며, 방어 점검은 `scripts/defense_check.py`(루프백만 허용), 계획·결과는 `docs/실측_검증계획_A.md`·`docs/검증결과_A_*.md`에 있다.
- DB 접근은 `app/db.py`만 거친다. SQL은 상수 문자열 + params로만 호출하고(AST 정적 검사), 응답이 400 미만일 때만 커밋하며 그 외에는 롤백한다. 일반 표는 `nexus_app`, 기밀 표는 `nexus_conf`(`conf=True`)로 분리한다.
- 사용자·역할(`employee`/`manager`/`admin`)은 요청마다 **DB에서 다시 조회**한다. 세션 값만 믿지 않아 잠금·권한 회수가 즉시 반영된다.

## 5. DB 설계와 최소권한

**표 12개 ([db/schema.sql](../db/schema.sql)):** `users`(부서 `dept` 포함), `employees`(주소록, `user_id` 연결), `documents`, `confidential_documents`, `payroll`(기밀), `financial_reports`(기밀), `posts`(`board`: 공지/자유), `attachments`, `chat_messages`(본인 대화만), `expenses`, `approvals`(문서 상태: pending/approved/rejected/withdrawn, 현재 단계), `approval_steps`(결재선: 순서·결재자·단계 상태·반려 사유. 순서와 결재자는 문서 안에서 유일, 1~5단계, 상신자 본인 지정은 트리거 `trg_steps_no_self_approval`이 거부).
기밀 표 3개(`confidential_documents`, `payroll`, `financial_reports`)는 `nexus_conf` 계정만 읽는다. 확장 단계 표는 필수 단계 완료 후 추가하며, 새 표마다 접근 계정과 GRANT를 이 절에 먼저 정의한다.

| 계정 | 권한 | 비고 |
|---|---|---|
| `nexus_app` | users(SELECT/INSERT + **UPDATE는 `password_hash`·`failed_count`·`locked_until`·`role` 열만**), employees·documents(SELECT), posts·attachments(SELECT/INSERT/DELETE), chat_messages(SELECT/INSERT), expenses·approvals·approval_steps(SELECT/INSERT + **상태 전이 열만 UPDATE**) | 기밀 표 접근 없음. DELETE는 게시판·첨부만(경비·결재는 이력 보존). 경비는 `status`, 결재 문서는 `status`·`current_step`·`decided_at`, 결재 단계는 `status`·`reason`·`decided_at` 열만 수정 가능해 소유자·금액·상신자·결재자를 앱 계정이 바꿀 수 없다 |
| `nexus_conf` | confidential_documents·payroll·financial_reports(SELECT) | 기밀 권한 확인 후에만 사용. Security Gateway가 쓸 계정 |
| root | 초기화·시드 전용 | 앱에서 사용 안 함 |

권한 정의: [db/grants.sql](../db/grants.sql). 비밀번호는 `.env`에서만 읽고 코드·문서에 넣지 않는다.

## 6. 앱 이벤트 로그 출력 (C와의 접점)

**역할 분담:** 앱에서 이벤트를 로그로 출력하는 코드는 A(홍주형)가 구현한다. 필드 형식과 이벤트 종류는 아래 **A의 초안**을 기준으로 구현한다. C(김태빈)는 이 형식에 맞춰 Graylog 입력·이벤트를 직접 구성하며, A는 C의 확정을 기다리지 않는다. Wazuh 룰, Graylog 입력·이벤트 정의, 탐지 튜닝은 C 담당이다.

모든 이벤트가 같은 필드를 가진다(초안): `ts, event_type, user, role, src_ip, method, path, decision, reason` (+ 이벤트별 부가 필드).

| event_type | 시점 |
|---|---|
| `login_success` / `login_failure` / `login_locked` | 로그인 결과 |
| `authz_deny` | 권한 부족 접근 |
| `csrf_fail` | CSRF 검증 실패 |
| `upload_reject` | 업로드 검증 실패 |
| `admin_action` | 관리자 변경 작업 |
| `not_found` / `rate_limited` | 404, IP 제한 |
| `suspicious_input` | 인젝션·XSS·경로 탐색 형태의 입력(WARN, 차단하지 않음) |

구현된 이벤트 전체 목록과 필드, C용 룰 제안은 [실측_검증계획_A.md](실측_검증계획_A.md) 4절에 있다.

이 파일을 Wazuh `localfile`로 수집하는 설정과 탐지 룰은 C가 진행한다. 형식이 확정되면 이 절을 갱신한다.

## 7. 이후 확장 시 구조 원칙

## 8-1. 화면 디자인 방향

- **톤(2026-10-19 개편, 사용자가 준 CleanPay 스타일 화면을 기준으로):** 흰 상단바(로고·가로 메뉴·사용자·로그아웃), 메뉴 이름이 파란 탭으로 채워지고 아래로 하위 메뉴가 펼쳐지는 구조, 왼쪽에는 지금 그룹의 이름과 하위 메뉴를 보여 주는 좁은 짙은 남색 레일, 청회색 바탕 위에 큰 제목과 흰 카드(얇은 그림자)와 가로 구분선만 있는 표, 테두리 있는 상태 배지. 강조색은 파랑(`--pen`, 행동·활성), 초록(`--ok`, 완료), 주황(`--warn`, 대기), 빨강(`--seal`, 반려·기밀·잠금)이다. 이전 "서류철" 톤(카드·그림자 없음)은 폐기했다. 하위 메뉴는 마우스를 올리거나 키보드로 들어오면 열린다(숨길 때 `display:none` 대신 투명하게 만들어 Tab이 닿는다). 메뉴는 `base.html` 한 곳에서 정의해 상단 메뉴·레일·브레드크럼이 같이 쓰고, 역할에 맞지 않는 항목은 아예 출력하지 않는다.
- **한 가지 기억할 디테일(유지):** 결재 상세의 **결재란**(상신·n차 결재 칸, 승인·반려 도장, 지금 차례 칸 강조)과 기밀 화면(기밀 문서·급여·재무)의 **기밀 도장**. 나머지는 의도적으로 조용하게 둔다.
- **규칙:** 상태는 색뿐 아니라 글자와 테두리 모양으로도 구분한다. 인라인 스타일·스크립트·외부 글꼴은 쓰지 않는다(CSP). 글꼴은 시스템 글꼴. 모든 입력 칸에 라벨, 본문 건너뛰기 링크, 현재 위치 표시, 포커스 표시, 좁은 화면(860px 이하) 대응. 색 대비는 WCAG AA(4.5:1)를 테스트가 CSS에서 직접 계산해 지킨다.
- 새 화면(S7 챗봇 포함)은 이 어휘(서류 본문, 장부형 표, 상태 표시, 필요 시 도장)를 그대로 쓴다. 구현: `app/static/style.css`, `app/templates/base.html`·`_ui.html`.

## 10. 메신저(nexus-messenger) 연동

별도 프로젝트 **nexus-messenger**(Flutter, 데스크톱+모바일, `C:\Users\stuls\Desktop\Agent\nexus-messenger`)가
nexus-work 계정으로 로그인해 직원끼리 1:1·그룹 채팅을 한다. 네이티브 앱은 쿠키를 못 쓰므로
세션과 완전히 별도인 **토큰 인증**(`Authorization: Bearer`)을 새로 추가했고(`app/messenger_api.py`,
`/api/v1/*`), 실시간 전송은 Flask-SocketIO(`app/realtime.py`)를 썼다. 아이디·비밀번호 확인
로직은 웹 로그인과 **같은 함수**(`app/auth.py`의 `authenticate()`)를 공유해 브루트포스 방어가
두 곳에서 따로 놀지 않는다. 새 표 4개(`api_tokens`·`conversations`·`conversation_members`·
`messenger_messages`)는 전부 `nexus_app` 계정만 쓰고 기밀 표는 없다.

전체 엔드포인트·요청/응답 모양·Socket.IO 프로토콜·보안 설계는 별도 문서
[docs/02_메신저_API.md](02_메신저_API.md)에 있다(그 문서만 읽어도 클라이언트를 구현할 수 있게
