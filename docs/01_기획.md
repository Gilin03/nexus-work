# NEXUS WORK — 앱·DB 하드닝 설계서 (역할 A)

작성일: 2026-10-17 · 담당: 홍주형(역할 A) · 상태: 설계 초안 (코드 구현 전)

## 1. 목적과 범위

- **목적:** 팀 프로젝트 NEXUS WORK(사내 업무 포털 + AI Agent 방어전)의 **웹 앱·DB 기반을 완전히 방어된 상태로** 만든다. 의도적 취약점은 지금 정하지 않는다. 나중에 D가 결정해 지정한 부분만 약화한다.
- **담당 범위(역할표):** 게시판 코드 방어(입력 검증, 쿼리 파라미터화, 업로드·인증 제한), 관리자 경로 보호, DB 최소권한. 도구: Flask, MySQL.
- **추가 확정 범위(2026-10-17):** AI 챗봇의 **화면과 엔드포인트**, 게시판 + **자유게시판**. 챗봇 응답 생성·Tool 호출 로직은 타 담당이다.
- **범위 밖(타 담당):** 챗봇 응답 생성·Tool 호출, Security Gateway, 보안 대시보드(D), n8n 연동 관리 API(D), Wazuh/Graylog/n8n 연동 설정. 단, 이들이 붙을 **접점**(앱 이벤트 로그 출력 — 형식은 C와 협의, 기밀 문서용 DB 계정)은 이 설계에서 제공한다. Wazuh·Graylog 설정과 탐지 룰은 C, 자동 대응은 D, 방화벽 연동은 B 담당이다.

### 1-1. 기능 범위 (2026-10-17 확정: 일반 회사 ERP + 그룹웨어 + NEXUS WORK)

NEXUS WORK는 **그룹웨어 + ERP 업무 시스템 위에 AI Agent 방어전을 얹은 포털**이다. 범위가 넓으므로 단계로 나눠 필수 단계를 먼저 완성한다. 화면은 목록·상세·간단한 입력 위주로 두고 복잡한 업무 규칙은 만들지 않는다.

| 구분 | 모듈 | 데이터·기능 | 민감도 | 단계 |
|---|---|---|---|---|
| 그룹웨어 | 로그인·권한 | employee/manager/admin | - | **필수** |
| 그룹웨어 | 문서함 | 일반 문서, 기밀 문서(M&A 계획 등) | 기밀 분리 | **필수** |
| 그룹웨어 | 직원 검색(주소록) | 이름·부서·내선 | 일반 | **필수** |
| 그룹웨어 | 게시판 | 공지·글, 첨부 | 일반 | **필수** |
| 그룹웨어 | 자유게시판 | 자유 글(첨부는 게시판과 같은 업로드 규칙) | 일반 | **필수** |
| 그룹웨어 | AI 챗봇 화면·엔드포인트 | 대화 입력, 응답 표시, 대화 기록 | 본인 대화만 | **필수** |
| 그룹웨어 | 전자결재 | 결재 상신·승인·반려 | 본인·결재선만 | **필수** |
| 그룹웨어 | 일정, 메일 | 화면 위주 | 본인 | 확장 |
| ERP | 인사 | 직원 정보(일반), 급여(기밀) | 급여=기밀 | **필수** |
| ERP | 경비 | 경비 신청, 결재 연동 | 본인·팀 | **필수** |
| ERP | 재무 | 월 손익 보고(기밀) | 기밀 | **필수** |
| ERP | 구매·발주, 고객·영업 | 발주서, 거래처, 고객 목록 | 일반~팀 | 확장 |
| 관리자 | 사용자·권한 관리 | 역할 변경, 잠금 해제 | 관리자 | **필수** |
| 방어 | 챗봇 응답 생성·Tool 호출, Security Gateway, 보안 대시보드(D), n8n 관리 API(D), 탐지·대응 | 타 담당 | - | 팀 |

접근 규칙(서버에서 강제): 직원=본인 데이터, 매니저=팀 데이터, 관리자=전체, 기밀=별도 DB 계정과 별도 권한 확인.

**ERP 모듈 범위 제한(확정):** 인사·급여, 경비, 재무는 **시드 데이터(미리 넣어 둔 예시 데이터) + 목록·상세 화면까지만** 구현한다. 급여 계산, 경비 정산, 회계 처리 같은 복잡한 업무 규칙은 만들지 않는다. 접근 통제(본인·팀·기밀)는 이 범위에서도 그대로 적용한다.

## 3. 아키텍처

```
브라우저 → Flask 앱 ──(nexus_app 계정)──→ MySQL: users, employees, documents, posts, attachments, chat_messages
              │
              ├─(nexus_conf 계정, 기밀 권한 확인 후에만)→ MySQL: confidential_documents
              ├─ 업로드 파일 → instance/uploads (웹루트 밖, 무작위 이름)
              └─ 보안 로그 → logs/security.jsonl (JSON Lines, Wazuh 수집 대상)
```

- 앱 구성: `config` · `db` · `validators` · `security`(로그·CSRF·헤더·제한) · `uploads` — **S2 완료**. `auth`(로그인·로그아웃·세션·잠금·비밀번호 변경·`login_required`/`role_required`) — **S3 완료**. `portal`(문서함·기밀 문서함·직원 검색·게시판·자유게시판·첨부) — **S4 완료**. `erp`(급여·재무 보고·경비)·`approvals`(전자결재) — **S5 완료**. `admin`(사용자 목록·역할 변경·잠금 해제) — **S6 완료**. `chat`(챗봇 화면·엔드포인트) — **S7 완료**.
- 챗봇 동작(S7, 구현·검증됨, H16): 로그인·CSRF 필수, 메시지 1~2,000자와 제어문자 검증, 사용자당 분당 20회 제한, **대화 기록은 본인 것만**(팀장·관리자도 본인 것만) 저장·조회, 폼으로 사용자·화자를 바꿀 수 없다. **응답은 신뢰하지 않는다:** 글자로만 취급해 이스케이프하고(HTML·`javascript:` 해석 안 함), 제어문자 제거와 8,000자 제한을 거치며, 응답기 예외는 가두어 내부 정보 없이 안내 문구만 보인다. 사용자 메시지는 응답을 기다리기 전에 먼저 확정한다. 보안 로그에는 대화 내용 대신 글자 수만 남긴다(내용은 `chat_messages`에만 있다).
- **다른 담당과의 접점(응답기):** 실제 AI 응답과 Tool 호출은 다른 담당 몫이며 `app.config["CHAT_RESPONDER"]`를 `responder(user, message, history) -> str`로 교체해 연결한다(기본값은 시험 응답). `user`는 지금 로그인한 사용자이고, **챗봇의 권한은 이 사용자의 권한을 넘을 수 없다**(Tool 호출마다 Security Gateway가 사용자·역할·자원 권한을 다시 검사). `history`는 본인의 최근 10건이다. 응답기는 자체 시간 제한을 둬야 한다.
- 관리자 동작(S6, 구현·검증됨): `/admin/*`은 블루프린트 단위로 role=admin을 서버에서 검사하고(비로그인은 로그인 화면, 그 외는 403), 변경은 POST+CSRF만 허용한다(H9). 역할 변경은 즉시 반영되며(사용자·역할은 요청마다 DB 재조회), **본인 역할은 바꿀 수 없다**(그래서 관리자가 0명이 되지 않는다). 역할 값은 허용목록(employee/manager/admin)만 받고, 화면을 연 뒤 다른 곳에서 바뀐 사용자는 덮어쓰지 않는다(409). 강등되어 팀장·관리자 권한을 잃은 사람은 결재선에 이미 지정되어 있어도 결재를 처리할 수 없다(`approver_role_revoked`). 잠금 해제는 실패 횟수와 잠금 시각을 함께 초기화한다. 모든 변경과 거부는 `admin_action` 이벤트로 남고, 비밀번호 해시는 화면에 내보내지 않는다. 앱 DB 계정은 `users`에서 로그인 처리·역할 변경에 필요한 4개 열만 수정할 수 있다. 사용자 생성·삭제·비밀번호 초기화·수동 잠금은 범위에 넣지 않았다(자동 잠금·회수는 D의 n8n 담당).
- ERP·결재 동작(S5, 구현·검증됨): 접근 범위는 직원=본인, 팀장=같은 부서, 관리자=전체이며 서버에서 강제한다(H14). 급여·재무는 기밀 DB 계정으로만 읽고 재무 보고는 manager·admin만 본다. 경비는 항상 임시저장으로 시작해 소유자 본인만 제출할 수 있다.
- **결재선(상신자가 결정):** 상신자가 팀장·관리자 중 최대 5명을 **순서대로** 고른다(경비 제출과 일반 결재 상신 모두). 본인·중복·일반 직원은 지정할 수 없고(앱 검사, 본인은 DB 트리거도 거부), 잘못된 선택이면 400으로 되돌아가며 경비 상태는 바뀌지 않는다.
- **순차 결재:** 첫 결재자만 `pending`, 나머지는 `waiting`. 지금 차례인 결재자만 승인·반려할 수 있고(차례 전 결재자는 403 `not_your_turn`, 결재선에 없는 사람은 관리자라도 403), 승인하면 다음 결재자에게 차례가 넘어가며, 마지막 승인이 나면 문서와 연결 경비가 승인된다.
- **반려:** 사유(1~500자)가 필수이며 어느 단계에서든 반려하면 문서와 경비가 반려되고 남은 단계는 `skipped`가 된다. 반려된 경비는 종결 상태다(재상신 불가).
- **철회:** 상신자 본인만, 첫 결재자가 처리하기 전(진행 중이고 1단계)에만 가능하다. 철회하면 문서는 `withdrawn`, 단계는 `skipped`, 연결 경비는 임시저장으로 돌아가 고쳐서 다시 상신할 수 있다. 첫 결재 뒤·종결 후에는 409.
- 종결 상태(승인·반려·철회)는 바꿀 수 없고(H15), 승인과 철회가 동시에 오면 문서 행 잠금으로 한쪽만 성공한다.
- 포털 동작(S4, 구현·검증됨): 기밀 문서는 manager·admin만 열람하고 기밀 DB 계정으로만 조회한다. 공지 쓰기는 manager·admin만, 자유게시판은 로그인한 모두가 쓴다. 글 삭제는 작성자 또는 admin만. 첨부는 pdf·png·jpg·txt만 허용하고 확장자와 내용이 모두 맞아야 하며, 서버가 만든 uuid 이름으로 `instance/uploads`에만 저장하고 항상 다운로드로만 내려준다. 직원 검색의 LIKE 와일드카드는 문자 그대로 취급한다.
- 인증 동작(S3, 구현·검증됨): 로그인 실패 메시지는 원인과 무관하게 동일, 5회 실패 시 15분 잠금(잠긴 동안은 맞는 비밀번호도 거부), 로그인 성공 시 세션·CSRF 토큰 재발급, 유휴 30분·절대 8시간 만료, 사용자·역할·잠금은 요청마다 DB 재조회. 세션은 서명된 쿠키지만 `users.session_version`과 맞아야 유효하다. 로그아웃·비밀번호 변경은 이 값을 올려 이전 쿠키(다른 기기 포함)를 모두 무효로 만든다(S8). 기기별 개별 폐기는 서버 측 세션 표가 필요해 하지 않았다.
- 점검·로그(S8): 비로그인으로 열리는 화면은 `/login`·`/healthz`뿐이며 테스트가 라우트 목록 전수로 확인한다. 의심 입력(SQL 인젝션·XSS·경로 탐색 형태)은 차단하지 않고 `suspicious_input` 이벤트로 기록해 탐지(C)가 쓰게 한다. 실행은 `python run.py`(서버 버전 비노출, 기본 루프백)이며, 방어 점검은 `scripts/defense_check.py`(루프백만 허용), 계획·결과는 `docs/실측_검증계획_A.md`·`docs/검증결과_A_*.md`에 있다.
- DB 접근은 `app/db.py`만 거친다. SQL은 상수 문자열 + params로만 호출하고(AST 정적 검사), 응답이 400 미만일 때만 커밋하며 그 외에는 롤백한다. 일반 표는 `nexus_app`, 기밀 표는 `nexus_conf`(`conf=True`)로 분리한다.
- 사용자·역할(`employee`/`manager`/`admin`)은 요청마다 **DB에서 다시 조회**한다. 세션 값만 믿지 않아 잠금·권한 회수가 즉시 반영된다.

## 4. 하드닝 통제 목록 (통제 → 막는 위협 → 구현 → 검증)

| # | 영역 | 막는 위협 | 구현 방식 | 검증 |
|---|---|---|---|---|
| H1 | 쿼리 | SQL 인젝션 | 전 쿼리 `%s` 파라미터화, 문자열 결합 금지, LIKE 와일드카드 이스케이프 | 소스 정적 검사 테스트 + 입력 테스트 |
| H2 | 입력 | 형식 오류·로그 오염 | 허용목록 검증(사용자명 정규식, 길이, 제어문자, 정수 범위) | 단위 테스트 |
| H3 | 출력 | XSS | Jinja 자동 이스케이프, `\|safe` 금지, CSP(인라인 스크립트 불가) | 응답 헤더·템플릿 검사 |
| H4 | 비밀번호 | 크리덴셜 노출 | Argon2id 해시, 정책(12자 이상·복잡도·사용자명 포함 금지) | 단위 테스트 |
| H5 | 로그인 | 브루트포스·계정 열거 | 5회 실패 시 15분 잠금, IP당 분당 제한, 동일 오류 메시지, 미존재 계정도 더미 해시 검증 | 통합 테스트 |
| H6 | 세션 | 세션 고정·탈취 | 로그인 시 세션 재발급, HttpOnly·SameSite=Lax·Secure, 30분 만료 | 통합 테스트 |
| H7 | CSRF | 요청 위조 | 세션 토큰 + 모든 변경 요청 검증 | 통합 테스트 |
| H8 | 인가 | 권한 상승·IDOR | 서버에서 role·자원 소유 확인, 기밀 문서는 manager 이상 + 별도 DB 계정 | 통합 테스트 |
| H9 | 관리자 | 관리자 경로 노출 | `/admin/*` 전체에 블루프린트 단위로 role=admin 서버 검사(새 경로도 자동 적용), 변경은 POST+CSRF, 본인 역할 변경 금지, 변경 이력 로그 | 통합 테스트(라우트 목록 전수 검사) + 변이 검증 |
| H10 | 업로드 | 악성 파일 | 확장자 허용목록(pdf/png/jpg/txt) + 매직바이트 일치, 이중 확장자 거부, 2MB 상한, 무작위 이름·웹루트 밖 저장, 다운로드는 첨부 강제 | 단위+통합 테스트 |
| H11 | DB 권한 | 앱 침해 시 피해 확대 | 계정 분리(아래 5절), DDL·FILE·SUPER 없음, `local-infile` 끔 | 권한 SQL 점검 |
| H12 | 로그 | 탐지 불가·로그 위조 | 6절 초안 형식으로 이벤트 출력, 비밀 미기록, JSON 직렬화로 개행 삽입 방지 | 로그 형식 테스트 |
| H13 | 오류 | 정보 노출 | 디버그 끔, 일반 오류 페이지, 스택트레이스 미노출 | 통합 테스트 |
| H14 | 소유권·팀 범위 | 타인 데이터 열람(IDOR) | 경비·결재·급여는 본인/결재선/팀 소속을 서버에서 확인, ID 추측으로 접근 불가 | 통합 테스트 |
| H15 | 결재 무결성 | 결재 위조·자기 승인·순서 건너뛰기·결재선 조작 | 상신자가 정한 결재선(최대 5명, 팀장·관리자, 본인·중복 불가)으로 순차 결재, 지금 차례인 결재자만 처리, 상태 전이 허용목록, 반려 사유 필수, 철회는 첫 결재 전·상신자만, 결재자 열은 앱 계정 수정 불가 + DB 트리거·유일 제약 | 통합 테스트 + 변이 검증 |
| H16 | 챗봇 화면·엔드포인트 | 챗봇 응답을 통한 XSS, 타인 대화 열람, 남용 | 입력 길이 제한·CSRF, **챗봇 응답도 신뢰하지 않고 이스케이프**(HTML 해석 금지), 대화 기록은 본인만, 사용자당 요청 속도 제한 | 통합 테스트 |

## 5. DB 설계와 최소권한

**표 12개 ([db/schema.sql](../db/schema.sql)):** `users`(부서 `dept` 포함), `employees`(주소록, `user_id` 연결), `documents`, `confidential_documents`, `payroll`(기밀), `financial_reports`(기밀), `posts`(`board`: 공지/자유), `attachments`, `chat_messages`(본인 대화만), `expenses`, `approvals`(문서 상태: pending/approved/rejected/withdrawn, 현재 단계), `approval_steps`(결재선: 순서·결재자·단계 상태·반려 사유. 순서와 결재자는 문서 안에서 유일, 1~5단계, 상신자 본인 지정은 트리거 `trg_steps_no_self_approval`이 거부).
기밀 표 3개(`confidential_documents`, `payroll`, `financial_reports`)는 `nexus_conf` 계정만 읽는다. 확장 단계 표는 필수 단계 완료 후 추가하며, 새 표마다 접근 계정과 GRANT를 이 절에 먼저 정의한다.

| 계정 | 권한 | 비고 |
|---|---|---|
| `nexus_app` | users(SELECT/INSERT + **UPDATE는 `password_hash`·`failed_count`·`locked_until`·`role` 열만**), employees·documents(SELECT), posts·attachments(SELECT/INSERT/DELETE), chat_messages(SELECT/INSERT), expenses·approvals·approval_steps(SELECT/INSERT + **상태 전이 열만 UPDATE**) | 기밀 표 접근 없음. DELETE는 게시판·첨부만(경비·결재는 이력 보존). 경비는 `status`, 결재 문서는 `status`·`current_step`·`decided_at`, 결재 단계는 `status`·`reason`·`decided_at` 열만 수정 가능해 소유자·금액·상신자·결재자를 앱 계정이 바꿀 수 없다 |
| `nexus_conf` | confidential_documents·payroll·financial_reports(SELECT) | 기밀 권한 확인 후에만 사용. Security Gateway가 쓸 계정 |
| root | 초기화·시드 전용 | 앱에서 사용 안 함 |

권한 정의: [db/grants.sql](../db/grants.sql). 비밀번호는 `.env`에서만 읽고 코드·문서에 넣지 않는다.

## 6. 앱 이벤트 로그 출력 (C와의 접점)

**역할 분담:** 앱에서 이벤트를 로그로 출력하는 코드는 A(홍주형)가 구현한다. 필드 형식과 이벤트 종류는 아래 **A의 초안**을 기준으로 구현한다. C(김태빈)는 이 형식에 맞춰 Graylog 입력·이벤트를 직접 구성하며, A는 C의 확정을 기다리지 않는다. Wazuh 룰, Graylog 입력·이벤트 정의, 탐지 튜닝은 C 담당이다.

모든 이벤트가 같은 필드를 가진다(초안): `ts, event_type, user, role, src_ip, method, path, decision, reason` (+ 이벤트별 부가 필드).

| event_type | 시점 |
|---|---|
| `login_success` / `login_failure` / `login_locked` | 로그인 결과 |
| `authz_deny` | 권한 부족 접근 |
| `csrf_fail` | CSRF 검증 실패 |
| `upload_reject` | 업로드 검증 실패 |
| `admin_action` | 관리자 변경 작업 |
| `not_found` / `rate_limited` | 404, IP 제한 |
| `suspicious_input` | 인젝션·XSS·경로 탐색 형태의 입력(WARN, 차단하지 않음) |

구현된 이벤트 전체 목록과 필드, C용 룰 제안은 [실측_검증계획_A.md](실측_검증계획_A.md) 4절에 있다.

이 파일을 Wazuh `localfile`로 수집하는 설정과 탐지 룰은 C가 진행한다. 형식이 확정되면 이 절을 갱신한다.

## 7. 이후 확장 시 구조 원칙

- 통제(H1~H16)는 **기능별로 분리된 함수·모듈**로 둔다. 나중에 D가 "이 부분을 취약하게"라고 지정하면 해당 모듈 하나만 바꿔도 되도록 한다.
- 취약 버전을 만들 때는 **D가 결정해 지정한 항목만** 약화하고, 그 위치는 저장소 밖 비공개 문서(`_private/`, Git 제외)에만 기록한다.

## 8. 검증 계획

- 자동 테스트: `pytest` — 검증 로직·정적 SQL 검사·헤더·인증·인가·업로드·잠금·CSRF.

## 8-1. 화면 디자인 방향

- **톤:** 서류철. 사무용 잉크 남색 사이드바, 복사지색 바탕, 흰 서류 본문, 괘선 있는 장부형 표. 카드·그림자·그라데이션은 쓰지 않는다. 강조색은 만년필 블루(행동·승인)와 인주 빨강(반려·기밀·잠금) 둘뿐이다.
- **한 가지 기억할 디테일:** 결재 상세의 **결재란**(상신·n차 결재 칸, 승인·반려 도장, 지금 차례 칸 강조)과 기밀 화면(기밀 문서·급여·재무)의 **기밀 도장**. 나머지는 의도적으로 조용하게 둔다.
- **규칙:** 상태는 색뿐 아니라 글자와 테두리 모양으로도 구분한다. 인라인 스타일·스크립트·외부 글꼴은 쓰지 않는다(CSP). 글꼴은 시스템 글꼴. 모든 입력 칸에 라벨, 본문 건너뛰기 링크, 현재 위치 표시, 포커스 표시, 좁은 화면(860px 이하) 대응. 색 대비는 WCAG AA(4.5:1)를 테스트가 CSS에서 직접 계산해 지킨다.
- 새 화면(S7 챗봇 포함)은 이 어휘(서류 본문, 장부형 표, 상태 표시, 필요 시 도장)를 그대로 쓴다. 구현: `app/static/style.css`, `app/templates/base.html`·`_ui.html`.

## 9. 공유와 비밀 관리

- 코드는 **GitHub 비공개(private) 저장소**로 팀과 공유한다. (저장소 생성·푸시는 아직 하지 않음)
- `.env`(DB 비밀번호, SECRET_KEY)와 `_private/`는 `.gitignore`로 제외한다. 팀원은 `.env.example`을 복사해 각자 값을 채운다. 발표 자료·README에도 비밀번호·API Key를 쓰지 않는다.
- Windows 줄바꿈(CRLF)으로 `db/init.sh`가 깨지지 않게 `.gitattributes`에 `*.sh text eol=lf`를 추가할 예정이다.
