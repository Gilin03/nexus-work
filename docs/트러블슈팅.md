# 트러블슈팅

## 2026-10-17 · 호스트 3306 포트 충돌

- **문제:** Docker MySQL을 기본 포트 3306에 열려고 보니 PC에 이미 `mysqld`(PID 7748)가 3306을 쓰고 있었다.
- **시도:** 기존 MySQL을 건드리지 않고, 컨테이너의 호스트 쪽 포트만 바꾸기로 했다.
- **해결:** `docker-compose.yml`의 포트를 `127.0.0.1:${DB_PORT:-3307}:3306`으로 바꾸고 `.env`, `.env.example`의 `DB_PORT`를 3307로 맞췄다. 컨테이너 내부 포트는 3306 그대로다.
- **배운 점:** 팀원 PC에도 로컬 MySQL이 있을 수 있다. 포트를 `.env`로 바꿀 수 있게 두면 각자 충돌을 피할 수 있다.
- **확인:** 컨테이너가 `127.0.0.1:3307->3306/tcp`로 뜨고, 계정 권한 점검을 통과했다.

## 2026-10-17 · 앱 계정의 UPDATE 권한이 줄어들지 않음

- **문제:** 경비·결재·사용자 표의 UPDATE 권한을 필요한 열로만 줄이려고 `grants.sql`을 고치고 DB를 다시 만들었는데, 기존에 부여한 표 단위 권한이 그대로 남아 컬럼 제한이 효과가 없었다.
- **원인:** MySQL은 `DROP DATABASE`를 해도 `mysql.tables_priv`의 표 단위 권한을 지우지 않는다. 같은 이름의 표가 다시 생기면 권한도 되살아난다.
- **해결:** 앱 계정(`nexus_app`, `nexus_conf`)을 지우고 다시 만들거나, 기존 권한을 `REVOKE`한 뒤 열 단위로 다시 부여했다. 권한 시험(`tests/test_db_privileges.py`)에 "다른 열 UPDATE는 거부" 항목을 넣어 같은 문제를 잡도록 했다.
- **배운 점:** 권한을 줄이는 변경은 설정 파일만 보지 말고 실제 계정으로 거부되는지 시험해야 한다.

## 2026-10-17 · 실제 서버에서만 보인 서버 버전 헤더

- **문제:** 앱이 `Server: NEXUS`를 넣었는데 방어 점검에서 `Werkzeug/3.1.9 Python/3.14.6`이 그대로 노출됐다. 테스트 클라이언트로 만든 시험은 통과하고 있었다.
- **원인:** 개발 서버가 앱과 별개로 `Server` 헤더를 하나 더 붙여 응답에 헤더가 두 개였다. 테스트 클라이언트는 서버 계층을 거치지 않아 보이지 않았다.
- **해결:** 헤더를 `NEXUS` 하나로 내보내는 요청 처리기를 쓰는 `run.py`를 만들고, 실제 서버를 띄워 헤더 개수를 확인하는 시험을 추가했다.
- **배운 점:** 헤더·연결 단위 방어는 실제 서버를 거쳐야 검증된다. 블랙박스 점검이 필요한 이유다.

## 2026-10-17 · 방어 점검 스크립트가 자기 자신을 속도 제한에 걸리게 함

- **문제:** 점검 중 로그인 요청이 분당 20회 한도를 넘어 429가 나면서 점검용 계정 로그인이 실패했다.
- **해결:** 스크립트가 최근 60초 안의 로그인 횟수를 세어 한도에 가까우면 기다리도록 했다. 속도 제한 점검(D16)은 마지막에 일부러 한도를 넘긴다.
- **배운 점:** 점검 도구도 대상 시스템의 방어 규칙을 따라야 한다. 끝난 뒤 1분쯤 로그인이 막히는 것은 안내서에 적었다.

## 2026-10-17 · 테스트 도구와 검증 스크립트에서 생긴 문제들

| 문제 | 원인 | 해결 |
|---|---|---|
| pytest가 `environment variable is longer than 32767 characters` 오류 | 2만 자짜리 문자열을 파라미터로 써서 테스트 이름이 환경변수 한도를 넘음 | 긴 값에 짧은 `id`를 붙임 |
| 인자 없는 DB 조회가 `not enough arguments for format string` | PyMySQL이 빈 튜플 인자를 받으면 쿼리의 `%`를 서식으로 해석함 | 인자가 없으면 `None`을 넘김 |
| 정적 점검이 정상 코드를 위험하다고 판정 | 모듈 설명 문구에 적힌 `\|safe` 글자를 실제 사용으로 오인 | 설명 문구를 바꿈(검사 규칙은 그대로) |
| 변이 검증 스크립트가 중간에 죽어 파일이 변이된 채 남음 | 파이썬 출력 인코딩 오류로 예외 발생, 복구 코드가 실행되지 않음 | 바로 백업에서 복구하고, 이후 모든 스크립트를 `try/finally`로 바꿔 항상 복구되게 함 |
| 변이 하나가 "통과"로 나옴 | 셸 따옴표 처리 때문에 바꾸려던 패턴이 적용되지 않았음 | 패턴이 없으면 "결과 무효"로 표시하게 하고 그 결과는 쓰지 않음 |
| 브라우저 미리보기가 `nexus-work` 서버를 찾지 못함 | 미리보기 도구가 이 폴더가 아니라 상위 `Agent/.claude/launch.json`을 읽음 | 그 파일에 항목을 하나 추가(저장소에는 포함되지 않음) |

## 2026-10-18 · Docker Desktop(Windows)에서 "다른 IP에서 온 공격"을 재현할 수 없었음

- **문제:** 속도 제한(IP당 분당 20회)이 IP를 바꾸면 우회되는지 확인하려고 Kali 컨테이너에서 공격을 보냈는데, 서버 로그에는 전부 `src_ip: 127.0.0.1`로 찍혔다.
- **원인:** Docker Desktop(Windows, WSL2 백엔드)이 컨테이너→호스트 방향 트래픽에 헤어핀 NAT를 건다. `host.docker.internal`로 보내면 호스트의 루프백으로 그대로 바뀌고, 앱을 `--host 0.0.0.0`으로 열어 호스트의 실제 LAN IP로 접속을 바꿔봐도 Windows 가상 스위치가 출발지를 다시 호스트 자신의 IP로 바꿔버렸다(컨테이너의 진짜 IP `172.17.0.3`은 한 번도 보이지 않음).
- **해결:** 네트워크로 증명하는 대신 코드로 증명했다. `ip_rate_limited()`를 두 개의 서로 다른 가짜 IP 문자열로 직접 호출해, 한 IP의 한도를 다 써도 다른 IP는 독립적으로 허용됨을 확인했다(분당 20회 제한은 설계대로 **IP별로** 동작한다는 뜻 — 실제로 여러 진짜 IP를 가진 공격자에게는 우회될 수 있다는 것도 함께 확인된 셈이다. 이건 이 앱만의 결함이 아니라 IP 기반 속도 제한의 일반적인 한계다).
- **배운 점:** 로컬 PC 하나에 Docker Desktop만 있는 환경에서는 "진짜 여러 출발지 IP"를 안전하게 재현하기 어렵다. 네트워크 증명이 막히면 해당 로직을 직접 호출하는 코드 레벨 증명으로 바꾸는 게 더 정직하고 빠르다.

## 2026-10-18 · Git Bash가 Docker 명령의 컨테이너 내부 경로를 Windows 경로로 바꿔버림

- **문제:** `docker run -v volume:/volume ... tar czf /backup/x.tar.gz -C /volume .`처럼 컨테이너 **안쪽** 절대경로(`/backup`, `/volume`)를 쓰는 명령이 "`C:/Program Files/Git/backup/...`: 그런 파일이나 디렉터리가 없음" 오류를 냈다.
- **원인:** Git Bash(MSYS)가 `/`로 시작하는 인자를 자동으로 Windows 경로로 바꾼다. 호스트 쪽 마운트 경로(`/c/Users/...`)는 의도대로 바뀌어야 하지만, 컨테이너 안에서만 의미 있는 경로까지 똑같이 바뀌어버렸다.
- **해결:** 그 명령 앞에 `MSYS_NO_PATHCONV=1`을 붙여 경로 자동 변환을 껐다(Kali 컨테이너로 nmap 등을 돌릴 때도 같은 문제가 있었다 — 그때도 같은 방법으로 해결).
- **배운 점:** Windows에서 Git Bash로 `docker run`/`docker exec`에 컨테이너 내부 경로나 옵션 문자열을 넘길 때는 습관적으로 `MSYS_NO_PATHCONV=1`을 붙이는 게 안전하다.
