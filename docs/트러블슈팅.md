# 트러블슈팅

## 2026-10-17 · 호스트 3306 포트 충돌

- **문제:** Docker MySQL을 기본 포트 3306에 열려고 보니 PC에 이미 `mysqld`(PID 7748)가 3306을 쓰고 있었다.
- **시도:** 기존 MySQL을 건드리지 않고, 컨테이너의 호스트 쪽 포트만 바꾸기로 했다.
- **해결:** `docker-compose.yml`의 포트를 `127.0.0.1:${DB_PORT:-3307}:3306`으로 바꾸고 `.env`, `.env.example`의 `DB_PORT`를 3307로 맞췄다. 컨테이너 내부 포트는 3306 그대로다.
- **배운 점:** 팀원 PC에도 로컬 MySQL이 있을 수 있다. 포트를 `.env`로 바꿀 수 있게 두면 각자 충돌을 피할 수 있다.
- **확인:** 컨테이너가 `127.0.0.1:3307->3306/tcp`로 뜨고, 계정 권한 점검을 통과했다.

## 2026-10-17 · 앱 계정의 UPDATE 권한이 줄어들지 않음

- **문제:** 경비·결재·사용자 표의 UPDATE 권한을 필요한 열로만 줄이려고 `grants.sql`을 고치고 DB를 다시 만들었는데, 기존에 부여한 표 단위 권한이 그대로 남아 컬럼 제한이 효과가 없었다.
- **원인:** MySQL은 `DROP DATABASE`를 해도 `mysql.tables_priv`의 표 단위 권한을 지우지 않는다. 같은 이름의 표가 다시 생기면 권한도 되살아난다.
- **해결:** 앱 계정(`nexus_app`, `nexus_conf`)을 지우고 다시 만들거나, 기존 권한을 `REVOKE`한 뒤 열 단위로 다시 부여했다. 권한 시험(`tests/test_db_privileges.py`)에 "다른 열 UPDATE는 거부" 항목을 넣어 같은 문제를 잡도록 했다.
- **배운 점:** 권한을 줄이는 변경은 설정 파일만 보지 말고 실제 계정으로 거부되는지 시험해야 한다.

## 2026-10-17 · 실제 서버에서만 보인 서버 버전 헤더

- **문제:** 앱이 `Server: NEXUS`를 넣었는데 방어 점검에서 `Werkzeug/3.1.9 Python/3.14.6`이 그대로 노출됐다. 테스트 클라이언트로 만든 시험은 통과하고 있었다.
- **원인:** 개발 서버가 앱과 별개로 `Server` 헤더를 하나 더 붙여 응답에 헤더가 두 개였다. 테스트 클라이언트는 서버 계층을 거치지 않아 보이지 않았다.
- **해결:** 헤더를 `NEXUS` 하나로 내보내는 요청 처리기를 쓰는 `run.py`를 만들고, 실제 서버를 띄워 헤더 개수를 확인하는 시험을 추가했다.
- **배운 점:** 헤더·연결 단위 방어는 실제 서버를 거쳐야 검증된다. 블랙박스 점검이 필요한 이유다.

## 2026-10-17 · 방어 점검 스크립트가 자기 자신을 속도 제한에 걸리게 함

- **문제:** 점검 중 로그인 요청이 분당 20회 한도를 넘어 429가 나면서 점검용 계정 로그인이 실패했다.

- **배운 점:** 점검 도구도 대상 시스템의 방어 규칙을 따라야 한다. 끝난 뒤 1분쯤 로그인이 막히는 것은 안내서에 적었다.

## 2026-10-18 · Docker Desktop(Windows)에서 "다른 IP에서 온 공격"을 재현할 수 없었음

- **문제:** 속도 제한(IP당 분당 20회)이 IP를 바꾸면 우회되는지 확인하려고 Kali 컨테이너에서 공격을 보냈는데, 서버 로그에는 전부 `src_ip: 127.0.0.1`로 찍혔다.
- **원인:** Docker Desktop(Windows, WSL2 백엔드)이 컨테이너→호스트 방향 트래픽에 헤어핀 NAT를 건다. `host.docker.internal`로 보내면 호스트의 루프백으로 그대로 바뀌고, 앱을 `--host 0.0.0.0`으로 열어 호스트의 실제 LAN IP로 접속을 바꿔봐도 Windows 가상 스위치가 출발지를 다시 호스트 자신의 IP로 바꿔버렸다(컨테이너의 진짜 IP `172.17.0.3`은 한 번도 보이지 않음).
- **해결:** 네트워크로 증명하는 대신 코드로 증명했다. `ip_rate_limited()`를 두 개의 서로 다른 가짜 IP 문자열로 직접 호출해, 한 IP의 한도를 다 써도 다른 IP는 독립적으로 허용됨을 확인했다(분당 20회 제한은 설계대로 **IP별로** 동작한다는 뜻 — 실제로 여러 진짜 IP를 가진 공격자에게는 우회될 수 있다는 것도 함께 확인된 셈이다. 이건 이 앱만의 결함이 아니라 IP 기반 속도 제한의 일반적인 한계다).
- **배운 점:** 로컬 PC 하나에 Docker Desktop만 있는 환경에서는 "진짜 여러 출발지 IP"를 안전하게 재현하기 어렵다. 네트워크 증명이 막히면 해당 로직을 직접 호출하는 코드 레벨 증명으로 바꾸는 게 더 정직하고 빠르다.

## 2026-10-18 · Git Bash가 Docker 명령의 컨테이너 내부 경로를 Windows 경로로 바꿔버림

- **문제:** `docker run -v volume:/volume ... tar czf /backup/x.tar.gz -C /volume .`처럼 컨테이너 **안쪽** 절대경로(`/backup`, `/volume`)를 쓰는 명령이 "`C:/Program Files/Git/backup/...`: 그런 파일이나 디렉터리가 없음" 오류를 냈다.
- **원인:** Git Bash(MSYS)가 `/`로 시작하는 인자를 자동으로 Windows 경로로 바꾼다. 호스트 쪽 마운트 경로(`/c/Users/...`)는 의도대로 바뀌어야 하지만, 컨테이너 안에서만 의미 있는 경로까지 똑같이 바뀌어버렸다.
- **해결:** 그 명령 앞에 `MSYS_NO_PATHCONV=1`을 붙여 경로 자동 변환을 껐다(Kali 컨테이너로 nmap 등을 돌릴 때도 같은 문제가 있었다 — 그때도 같은 방법으로 해결).
- **배운 점:** Windows에서 Git Bash로 `docker run`/`docker exec`에 컨테이너 내부 경로나 옵션 문자열을 넘길 때는 습관적으로 `MSYS_NO_PATHCONV=1`을 붙이는 게 안전하다.

## 2026-10-19 · 새 PC로 옮길 때 DB 볼륨 복원 순서

- **문제:** 새 PC(`C:\Users\user\Desktop\nexus-work`)에는 저장소만 있고 `.env`·`.venv`·MySQL 컨테이너가 없었다. 이전 PC에서 만든 볼륨 백업(`nexus-mysql-data_20261018_214040.tar.gz`, MySQL 데이터 폴더 전체)으로 DB를 그대로 옮겨야 했다.
- **원인(주의점):** `docker compose up -d`를 먼저 하면 빈 볼륨에서 `db/init.sh`가 돌아 새 DB를 만든 뒤에 백업을 덮어쓰게 된다. 또 볼륨의 MySQL 계정 비밀번호는 이전 PC의 `.env` 값이라, 새로 만든 `.env`로는 접속할 수 없다.
- **해결:** 이전 PC의 `.env`를 그대로 가져오고, 다음 순서로 복원했다.
  1. `docker compose up --no-start`: 컨테이너와 빈 볼륨(`nexus-work_nexus-mysql-data`)만 만들고 MySQL은 켜지 않는다.
  2. 백업 안에 `../`나 절대경로가 없는지 `tar -tzf`로 먼저 확인한다(링크는 MySQL이 만드는 `mysql.sock` 하나뿐이었다).
  3. 압축을 푼다. `MSYS_NO_PATHCONV=1 docker run --rm -v nexus-work_nexus-mysql-data:/data -v "C:/Users/user/Downloads/<백업>.tar.gz:/backup.tar.gz:ro" alpine sh -c 'cd /data && tar xzpf /backup.tar.gz'` (`p`로 소유자 uid 999를 유지한다).
  4. `docker compose up -d`로 켜면 기존 데이터가 있어 `init.sh`가 돌지 않는다.
- **확인:** MySQL 8.4.11이 오류 없이 기동했다. `.env` 비밀번호로 root·`nexus_app`·`nexus_conf` 모두 접속됐고, 시드 데이터 건수가 맞았으며, `pytest` 453개가 모두 통과했다.
- **참고:** 함께 받은 `nexus-work-db-backup-2026-10-18.tar.gz`·`.zip`은 이름과 달리 DB가 아니라 커밋 `079303c` 시점의 소스 코드 묶음이었다. 이 PC의 Docker Desktop은 사용자별 설치 경로(`C:\Users\user\AppData\Local\Programs\DockerDesktop\`)에 있다.

## 2026-10-19 · 외부 접속: venv로 띄워도 방화벽은 기본 python.exe 규칙을 본다

- **문제:** 포털을 `0.0.0.0:5070`으로 열 때 Windows 방화벽 규칙이 필요한지 확인해야 했다. 셸은 관리자 권한이 아니어서 규칙을 새로 만들 수 없었다.
- **원인:** Windows의 `.venv\Scripts\python.exe`는 기본 인터프리터(`C:\Program Files\Python313\python.exe`)를 띄우는 실행기다. 실제로 포트를 여는 프로세스 경로를 `Get-Process -Id <PID>`로 보니 기본 `python.exe`였다. 이 PC에는 그 경로를 대상으로 한 규칙 "Python"(Public 프로필, 허용, TCP 모든 포트)이 이미 있었고, 학원 LAN은 Public 프로필이다.
- **해결:** 새 규칙을 만들지 않았다. 다른 PC에서 필요하면 관리자 PowerShell에서 `New-NetFirewallRule -DisplayName "NEXUS WORK 5070" -Direction Inbound -Protocol TCP -LocalPort 5070 -Action Allow`를 실행한다.
- **배운 점:** 같은 PC에서 자기 LAN 주소로 보내는 요청은 방화벽을 거치지 않고, Docker 컨테이너에서 보낸 요청도 출발지가 호스트 주소로 바뀐다(10-18 항목). 외부 접속은 결국 다른 장비에서 확인해야 한다.

- **채팅 시험의 `<script` 검사:** 화면에 `chat.js` 를 붙이자 "페이지 어디에도 `<script` 가 없어야 한다"는 기존 시험이 실패했다. 포털 자체의 같은 출처 스크립트를 뺀 나머지에 `<script` 가 없는지로 정확히 좁혔다(공격 문자열이 그대로 출력되지 않는다는 원래 의도는 같다).
- **내 실수:** `.env` 를 확인하면서 가림 처리를 `*_KEY=` 에만 걸어, 실습용 토큰과 새 n8n DB 비밀번호가 작업 세션의 명령 출력에 찍혔다. n8n 비밀번호는 전달 전이라 바로 `--rotate` 로 바꿨다. 실습용 토큰은 바꾸려면 시드를 다시 넣어야 해서 사용자 결정으로 남겼다.

## 2026-10-20 · n8n 전용 DB 계정

- **IP 로 묶은 MySQL 계정은 접속이 안 된다:** Docker Desktop(Windows)은 게시한 포트를 주소 변환으로 넘겨서, MySQL 은 루프백이든 LAN 이든 모든 접속을 Docker 게이트웨이(172.21.0.1)에서 온 것으로 본다(앱 계정 오류 메시지 `'nexus_app'@'172.21.0.1'` 로 이미 확인된 현상). 그래서 `nexus_n8n@192.168.7.77` 은 영원히 맞지 않는다. 계정은 `%` 로 만들고 장비 제한은 Windows 방화벽에서 한다.
- **방화벽 '허용' 규칙은 효과가 없다:** Docker Desktop 이 `com.docker.backend.exe` 에 Public 프로필·모든 원격 주소 허용 규칙을 만든다. 허용끼리는 하나만 맞아도 통과하므로, 제한하려면 "허용할 IP 를 뺀 전체 차단" 규칙을 써야 한다(`scripts/n8n_db_firewall.ps1`). 루프백 접속은 방화벽을 거치지 않아 포털은 영향이 없다.
- **pymysql 과 호스트 `%`:** 인자를 넘기는 `execute(sql, args)` 에서는 문장 안의 `'%'` 가 서식 문자로 해석돼 `unsupported format character` 가 난다. 인자를 쓰는 문장에서만 `%%` 로 바꾼다.
- **`ALTER USER` 순서:** `WITH MAX_USER_CONNECTIONS` 같은 자원 옵션이 `FAILED_LOGIN_ATTEMPTS` 같은 비밀번호 옵션보다 앞에 와야 한다(반대면 1064).
- **PowerShell 스크립트 한글:** Windows PowerShell 5.1 은 BOM 없는 `.ps1` 을 CP949 로 읽어 한글 메시지와 규칙 이름이 깨진다. UTF-8 BOM 으로 저장했다.

## 2026-10-19 · 인사 기능 개발 중 찾은 것들

- **문제 1(시드 스크립트 오류, 실행 전에 발견):** 근태 시드의 출근 시각을 `time(8, 50 + (…) % 20)`으로 만들어 분이 최대 69가 될 수 있었다(`ValueError: minute must be in 0..59`). 라이브 DB 채우기 스크립트를 먼저 돌리다 실패해서 알았고, 시드는 아직 돌리기 전이라 데이터는 안전했다.
- **해결:** `time(8, 50) + timedelta(minutes=…)`로 바꿔 두 곳(시드, 라이브 채우기)을 고쳤다. `nexus_test`에 시드를 돌려 근태 25건·출근 08:50~09:09를 확인하고 곧바로 비웠다.
- **문제 2(시험 코드): ** 빈 조회 결과를 `== []`로 비교했는데 DB 래퍼는 빈 튜플을 돌려줘서 시험이 실패했다. 앱 결함이 아니라 시험 오류였고 `assert not …`로 바꿨다.
- **문제 3(내 확인 스크립트): ** 화면 확인 뒤 만든 근태를 지우는 쿼리를 "최근 24시간"으로 넓게 썼다. 시드 근태 일부가 지워졌을 수 있어 바로 건수를 확인했고(모두 5건 그대로) 이상이 없었으나, 복구 쿼리는 만든 행만 정확히 가리켜야 한다.
- **MySQL 제약 하나:** `leave_requests.decided_by`에 `ON DELETE SET NULL`을 두면서 같은 열을 CHECK(결재자≠신청자)에 쓰면 MySQL이 거부한다(참조 동작이 있는 열은 CHECK에 쓸 수 없음). 그래서 `decided_by`는 기본 제약(RESTRICT)으로 두었고 시험 정리 쿼리는 휴가 행을 먼저 지운다.
- **이미 만들어진 DB:** `init.sh`는 최초 기동 때만 돌아 새 표·열이 반영되지 않는다. `python scripts/migrate_hr.py`(여러 번 실행해도 안전, 열·표·권한을 확인하며 추가)를 쓴다. 다른 팀원 PC의 DB에도 같은 스크립트를 한 번 실행해야 한다.

## 2026-10-19 · 자유게시판 그림·PDF 붙여넣기: 시험이 알려 준 것과 확인 방법

- **문제 1:** 붙여넣기용 스크립트(`paste-attach.js`)를 글쓰기 화면에 넣자 `tests/test_ui.py`의 "모든 화면 CSP 안전" 시험이 `<script`가 있다는 이유로 실패했다.
- **원인·해결:** 시험이 스크립트 태그를 전부 금지하고 있었지만 CSP의 취지는 *인라인* 스크립트 금지다. 같은 출처 `/static/*.js`를 `src`로 불러오는 태그만 허용하고 인라인 스크립트·`on…=` 핸들러·`style=`는 계속 금지하도록 시험을 좁혔다(느슨해진 것이 아니라 정확해진 것: 허용 형식이 아닌 `<script>`는 여전히 실패한다).
- **문제 2:** 실제 Chrome으로 PDF 미리보기를 확인하려는데 새 탭이 회색 화면만 나왔다. 응답 CSP(`default-src 'none'`) 때문인지 알 수 없었다.
- **원인·해결:** 같은 Chrome으로 CSP 없는 정상 PDF, 이 CSP, `object-src 'none'`, `sandbox`를 각각 열어 기준선을 만들었다. 모두 정상으로 그려졌고, 회색의 원인은 확인용으로 손으로 만든 PDF에 `xref` 표가 없었던 것이었다. 올바른 PDF로 바꾸자 실제 포털에서도 정상으로 보였다.
- **문제 3(확인 스크립트의 실수):** 처음 자동 확인이 등록이 안 됐는데, 첫 번째 `button[type=submit]`이 사이드바의 **로그아웃**이라 그걸 눌러 로그아웃된 것이었다. 앱의 결함이 아니고 `등록` 버튼을 정확히 지정해서 해결했다.
- **문제 4(내 실수, 사용자 서버 영향 가능):** 확인용 서버를 끌 때 `netstat`의 첫 번째 대기 프로세스를 골라 종료했는데, Windows는 같은 주소·포트에 중복 바인드를 허용해서(오류 없이 서버가 여러 개 뜸) 엉뚱한 프로세스를 끈 것으로 보인다. 확인 중 팀원 접속 기록(`leesh`, 11:01~11:09)이 있었으나 작업 후에는 `0.0.0.0` 대기 서버가 없어, 사용자가 띄워 둔 서버를 함께 종료했을 가능성이 있다.
- **배운 점:** (1) 시험이 실패하면 시험을 끄지 말고 무엇을 지키려는 시험인지 보고 정확히 좁힌다. (2) 브라우저 기능은 기준선(정상 입력·제약 없음)을 먼저 만들어야 원인을 가린다. (3) 포트로 프로세스를 찾아 끌 때는 첫 줄이 아니라 실행 명령줄을 확인해 내가 띄운 것만 끈다.
