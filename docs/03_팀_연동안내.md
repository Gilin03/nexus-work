## 1. 포털 접속

| 항목 | 값 |
|---|---|
| 포트 | **5070** (확정, 기획서 구성도와 같음) |
| 받는 주소 | `.env`의 `APP_HOST=0.0.0.0`이면 이 PC의 모든 네트워크에서 받는다. 저장소 기본값(`.env.example`)은 `127.0.0.1`(내 PC만) |
| 이 PC의 주소(2026-10-19 확인) | 학원 LAN `이더넷` **192.168.3.14**, VMware `VMnet2` **172.16.50.10**·**172.16.50.1** |
| 접속 예 | 학원 LAN: `http://192.168.3.14:5070` · VMnet2의 VM(Kali 등): `http://172.16.50.10:5070` |
| 상태 확인 주소 | `/healthz` (로그인 없이 `{"status":"ok"}`) |

### 실행

```bash
docker compose up -d                 # MySQL
.venv\Scripts\python run.py          # .env 의 APP_HOST·APP_PORT 대로 뜬다
.venv\Scripts\python run.py --host 127.0.0.1   # 잠깐 내 PC에서만 열 때(명령줄 값이 .env 보다 우선)
```

`APP_HOST`가 루프백이 아닌데 시드 비밀번호(`SEED_*_PW`)가 `.env.example`의 예시 값 그대로면, `run.py`가 기동할 때 `[주의]` 줄로 알려 줍니다. 기동을 막지는 않습니다. 다른 팀이 공격해 오는 환경에 열기 전에 `.env`에서 바꾸고 `python scripts/seed.py --reset --db nexus`로 다시 넣으세요.

### 방화벽

- **이 PC:** 따로 규칙을 만들지 않았습니다. 이미 있는 Windows 방화벽 규칙 "Python"(Public 프로필, 허용, `C:\Program Files\Python313\python.exe`, TCP 모든 포트)이 적용됩니다. `.venv\Scripts\python.exe`로 띄워도 실제로 포트를 여는 프로세스는 기본 `python.exe`라서(확인함) 이 규칙에 걸립니다. 학원 LAN은 Public 프로필입니다.
- **다른 PC에서 포털을 띄울 때:** 처음 실행하면 Windows가 허용 여부를 묻습니다. 미리 열려면 관리자 PowerShell에서 다음을 실행합니다.
  `New-NetFirewallRule -DisplayName "NEXUS WORK 5070" -Direction Inbound -Protocol TCP -LocalPort 5070 -Action Allow`

### 확인한 것과 못 한 것 (2026-10-19)

| 확인 | 결과 |
|---|---|
| `0.0.0.0:5070`에서 대기 | 됨 (`netstat`) |
| `192.168.3.14:5070`, `172.16.50.10:5070`으로 접속 | 둘 다 200 |
| Docker 컨테이너(172.17.0.3)에서 `192.168.3.14:5070`으로 접속 | 200. 다만 로그의 `src_ip`는 192.168.3.14로 찍힘(Docker Desktop NAT, [트러블슈팅](트러블슈팅.md) 10-18 항목과 같은 현상) |
| 팀장 계정으로 기밀 문서에 식별 문구·토큰이 보임, 직원 계정은 403 | 됨 (LAN 주소로 접속해 확인) |
| **이시헌 장비에서 접속(작업 계획서의 완료 기준)** | **아직 못 함.** 이 PC 안에서 보낸 요청은 방화벽을 거치지 않고, 컨테이너 요청도 출발지가 바뀌어서 대신 증명할 수 없다. 이시헌 장비에서 `http://<이 PC 주소>:5070/healthz` 확인 필요 |

### pfSense 경유만 허용 (5070 포트 직접 접속 차단)

- 이시헌 님(네트워크 담당) 구성: 포털 PC(`192.168.3.14:5070`)로의 직접 접속을 차단하고, pfSense(`192.168.3.10:5070`) 경유 요청만 허용.
- `scripts/portal_pfsense_only.ps1`(관리자 PowerShell) 또는 바탕화면 `포털_직접접속차단_방화벽규칙_적용.bat`:
  - 출발지 IP가 pfSense(`192.168.3.10`)가 아닌 모든 IPv4 대역(`0.0.0.0-192.168.3.9`, `192.168.3.11-255.255.255.255`) 및 IPv6 전체를 차단 규칙으로 등록.
  - 맥북 및 일반 사용자 PC에서 `192.168.3.14:5070`으로 직접 접속 시 차단.
  - pfSense 경유 `192.168.3.10:5070` 접속 시 pfSense의 SNAT(출발지 192.168.3.10)로 정상 허용.
  - 해제 시: `scripts/portal_pfsense_only.ps1 -Remove` 또는 바탕화면 `포털_직접접속차단_방화벽규칙_해제.bat` 실행.
  - 이 PC 안(127.0.0.1)의 로컬 접속은 영향 없음.

### 이시헌 님과 확인할 것

1. **출발지 IP가 바뀌지 않는지(가장 중요):** 앱은 TCP 연결 상대 주소(`remote_addr`)를 `src_ip`로 그대로 기록하고, 위조할 수 있는 `X-Forwarded-For`는 믿지 않습니다. pfSense가 공격망→포털 트래픽에 출발지 NAT를 걸면 모든 공격이 pfSense 주소 하나로 기록됩니다. 그러면 공격 팀별 구분(규칙 R1~R4, 출발지별 티켓·상황판)이 불가능해지므로, 포워딩·라우팅할 때 출발지 주소가 유지되는지 확인해 주세요. 확인 방법: Kali에서 `/no-such-page` 한 번 → `logs/security.jsonl`의 `not_found` 이벤트 `src_ip`가 Kali 주소인지 확인.
2. **VMnet2 주소:** 이 PC는 VMnet2에 `172.16.50.10`과 `172.16.50.1`을 함께 갖고 있습니다. 기획서 구성도에서 `.1`은 pfSense LAN, `.2`는 포털 서버, `.10`은 Graylog입니다. 이 PC에서 포털을 띄운다면 구성도의 `.2`와 실제 주소가 다르고, pfSense VM이 `.1`을 쓰면 주소가 겹칩니다. 통신표를 만들 때 맞춰 주세요.

기획서 4.1의 공격 체인이 실제로 이어지도록 기밀 문서에 시나리오 데이터를 넣었습니다(`scripts/seed.py`).

| 4. 내부 API 접근 | `M&A_PLAN`에서 얻은 **실습용 토큰**으로 내부 API 호출 |
| 5. 목표 달성 | **FLAG는 내부 API 응답**에서 나옴(7장 담당). 문서에는 넣지 않음 — 예전 시드는 문서에 FLAG를 넣어 3단계만으로 끝났으나, 기획서대로 바꿨다 |

| 기밀 문서 | 식별 문구 | 들어 있는 가상 비밀 |
|---|---|---|
| `M&A_PLAN` | `NXC-MNA-7Q4K` | 프로젝트 블루오로라: 인수 후보 오로라테크, 제안 상한 1,240억 원, 실사 마감 2026-11-30 + **내부 API 토큰** |
| `임원 보수 체계 개편안` | `NXC-EXC-2M8P` | 성과급 상한을 기본급의 180%로 조정, 2027년 1월 시행 |

기밀 문서는 지금처럼 팀장(lee, choi)·관리자(admin)만 열람할 수 있고, 직원은 403과 `authz_deny` 로그가 남습니다.

### 식별 문구 (`NXC-` — 비밀이 아니라 표지)

- 형식은 `NXC-<문서 약어 3자>-<4자>`이고, 정규식은 `NXC-[A-Z]{3}-[0-9A-Z]{4}`입니다. 문서마다 다르므로 어느 문서가 새어 나갔는지 바로 알 수 있습니다.
- 탐지 규칙과 증빙에 쓰도록 값을 저장소와 이 문서에 그대로 둡니다.
- **쓰는 곳(제안):** 게이트웨이(7장)가 AI 응답에서 이 문구를 발견하면 유출 이벤트를 남기고, 탐지(김태빈)는 그 이벤트를 R3의 보조 근거로 씁니다. 포털 보안 로그는 대화 원문을 남기지 않으므로(설계), 문구 검사는 응답을 만드는 쪽에서 해야 합니다. 시연 캡처에 이 문구가 보이면 "기밀 유출 성공"의 증빙이 됩니다.

### 실습용 토큰 (`nxapi_` — 비밀값)

- 값은 각 PC의 `.env`에 있는 `LAB_INTERNAL_API_TOKEN`입니다. 형식은 `nxapi_` + 임의 32자이며, **팀 채팅으로만 공유**합니다. 저장소의 시험(`test_real_secret_values_never_appear_in_publishable_files`)이 이 값이 올라갈 파일에 섞이지 않았는지 검사합니다.
- 내부 API(7장)는 같은 환경변수 값으로 토큰을 검사하면 됩니다. 포털을 띄우는 PC와 내부 API가 같은 값을 써야 체인이 이어집니다.
- `nxapi_` 접두어 덕분에 게시글·요청·로그에서 토큰이 드러난 흔적을 찾기 쉽습니다.
- **폐기·재발급(R4):** 지금은 `.env` 값 하나뿐이라 n8n이 폐기할 수 없습니다. 작업 계획서 4장의 DB 대응 열·n8n 계정 작업(10/20)에서 토큰을 DB로 옮길지(폐기 시각 열)를 진혜정·7장 담당과 함께 정합니다.

### 내부 API (`/internal/api/v1/flag`, 2026-10-20 반영)

- 이시헌 님의 `ai-agent` 브랜치(9db742a)에서 내부 API 부분만 main 으로 옮겼습니다(`app/internal_api.py`). AI 에이전트·대화방 부분은 아직 옮기지 않았습니다(AI 채팅과 충돌 9곳).
- `GET /internal/api/v1/flag` + `Authorization: Bearer <LAB_INTERNAL_API_TOKEN>` → `{"ok": true, "flag": ...}`. 틀리거나 없으면 401, 같은 IP 분당 30번 넘으면 429.
- **직접 호출을 막지는 않습니다.** 토큰이 맞으면 FLAG 를 줍니다(시나리오의 목표 지점). 대신 모든 호출을 `internal_api` 이벤트로 남깁니다: `via=direct`(HTTP 로 직접), `via=gateway`(나중에 AI 게이트웨이가 대신 호출), `token_fp`(토큰 지문 10자, 원문 아님), `src_ip`, `api_path`. 탐지 규칙 R4 는 `via=direct` 를 보면 됩니다. GELF 로 Graylog 에도 그대로 갑니다.
- FLAG 는 `.env` 의 `LAB_INTERNAL_API_FLAG` 에만 있습니다(이 PC 는 10-20 에 새 무작위 값으로 만듦, **팀 채팅으로만 공유**). 체크리스트에 적힌 기획서 FLAG 값은 쓰지 않습니다.

### 각자 PC에 적용하는 법

1. `.env`에 `LAB_INTERNAL_API_TOKEN=<팀 채팅으로 받은 값>`을 추가합니다. 이 값이 없거나 자리표시자면 `seed.py`가 멈추고 만드는 명령을 알려 줍니다.
2. `python scripts/seed.py --reset --db nexus`를 실행합니다. **주의: 모든 표를 비우고 시드로 다시 채웁니다**(메신저 표 포함, 직접 만든 글·대화·결재가 지워짐).
3. 팀장 계정으로 로그인해 `기밀 문서함 → M&A_PLAN`에서 식별 문구와 토큰을 확인합니다.

## 3. 팀원별 관리자 계정

팀원이 각자 포털에 들어가 화면과 기능을 직접 확인하도록 admin 역할 계정을 만들었습니다(`scripts/create_team_admins.py`).

| 아이디 | 이름 | 담당 |
|---|---|---|
| `hongjh` | 홍주형 | 웹·DB 하드닝(A) |
| `leesh` | 이시헌 | 네트워크(B) |
| `kimtb` | 김태빈 | 탐지(C) |
| `jinhj` | 진혜정 | 자동화·상황판(D) |

- 부서는 `보안관제팀`, 역할은 `admin`입니다. **2026-10-20부터 최고관리자로 고정되는 계정은 `admin`(시스템관리자)과 `hongjh` 둘뿐**입니다. 다른 팀원 계정(leesh·kimtb·jinhj)은 일반 관리자처럼 역할을 바꿀 수 있고, 관리자 역할인 동안 보안 대시보드(`/admin/audit`)를 엽니다. 사용자 삭제와 복구(재입사)는 두 최고관리자만 할 수 있습니다. 고정 계정의 비밀번호는 화면에서 초기화되지 않으므로 잊으면 이 PC에서 `create_team_admins.py --reset-initial`로 초기화합니다.
- **초기 비밀번호는 모두 `1234`입니다(사용자 결정, 2026-10-19).** 로그인한 뒤 화면 위쪽 **비밀번호 변경**(`/account/password`)에서 각자 바꿉니다. 새 비밀번호는 정책(12자 이상, 대·소문자·숫자·기호 중 3종, 아이디 미포함)을 지켜야 하며, `5678` 같은 약한 값은 변경 화면이 거부합니다(확인함). 바꾸면 그 계정의 다른 로그인 세션은 모두 끊깁니다.
- `1234`는 정책에 걸리는 값이라 `create_team_admins.py`가 해시를 DB에 직접 넣어 만든 것입니다. 일부러 약하게 둔 초기값이므로 **처음 로그인하자마자 바꾸세요.**
- 계정은 **이 PC의 DB**에만 있습니다. 다른 PC에서 포털을 띄우면 거기서도 같은 스크립트를 실행해야 합니다(초기 비밀번호는 똑같이 1234).
- 이미 있는 아이디는 건너뜁니다. `seed.py --reset`은 모든 표를 비우므로, 리셋한 뒤에는 스크립트를 다시 실행하세요. 누군가 비밀번호를 바꾼 뒤 `--reset-initial`을 주면 그 계정이 다시 1234로 돌아갑니다(잠금·세션도 초기화).
- 주의: **1234인 admin 계정이 남아 있는 채로 외부(0.0.0.0)에 열면, 접속할 수 있는 누구든 추측만으로 관리자 권한과 기밀 문서를 얻습니다.** 공방전·시연 전에 4명 모두 비밀번호를 바꿨는지 확인하거나 계정을 지우세요. 5회 실패 시 15분 잠금은 이 계정에도 적용됩니다.

## 4. n8n DB 접속 (A4, 진혜정 대응 워크플로)

2026-10-20 결정: **A안(n8n 이 DB 에 직접 접속)**, n8n 장비는 김태빈 님 n8n 장비 **192.168.3.15**(2026-10-21 이전)(위치가 정해지면 바꾼다). 고정 계정(`pinned = 1`, 보안관제팀·시스템관리자)은 **세션 종료만 자동**, 잠금은 알림 뒤 사람이 승인한다.

**접속 정보**

| 항목 | 값 |
|---|---|
| 주소 | 포털 PC `192.168.3.14`, 포트 `3307`, DB `nexus` |
| 계정 | `nexus_n8n` (비밀번호는 이 PC 의 `.env` 의 `N8N_DB_PASSWORD`, 채팅에 쓰지 않는다) |
| 읽기 | `users` 의 `username`, `pinned`, `locked_until`, `session_version`, `ai_restricted` 열만 |
| 쓰기 | `users` 의 `locked_until`, `session_version`, `ai_restricted` 열만 (INSERT·DELETE·다른 열·다른 표 불가). `ai_restricted` 는 10-20 저녁에 더함(R3 대응) |
| 보호 | 로그인 5회 실패 시 계정 1일 잠금, 동시 접속 5개 |

**n8n 이 쓰는 SQL (시험으로 확인한 모양)**

```sql
-- 조회
SELECT username, pinned, locked_until, session_version FROM users WHERE username = ?;
-- 잠금(고정 계정은 건드리지 않도록 pinned = 0 조건)
UPDATE users SET locked_until = DATE_ADD(NOW(), INTERVAL 15 MINUTE) WHERE username = ? AND pinned = 0;
-- 세션 종료(고정 계정 포함)
UPDATE users SET session_version = session_version + 1 WHERE username = ?;
-- R3 대응: AI 사용 제한 / 해제 (다음 AI 요청부터 바로 적용, 포털의 다른 기능은 그대로)
UPDATE users SET ai_restricted = 1 WHERE username = ?;
UPDATE users SET ai_restricted = 0 WHERE username = ?;
```

- **AI 제한(`ai_restricted`)**: 1 이면 그 사용자가 AI 어시스턴트에 질문해도 AI 를 부르지 않고 "보안 조치로 제한" 안내만 나가며, 포털 로그에 `ai_restricted_block`(DENY)이 남는다. 관리자 화면 사용자 목록에 **AI 제한** 표시가 뜬다. 해제는 n8n 으로 0 을 쓴다(포털 앱 계정은 이 열을 바꿀 수 없다). 열 이름·정의는 이시헌 님 `ai-agent` 브랜치와 같다.

- **잠금 시각은 반드시 `DATE_ADD(NOW(), …)`처럼 DB 시계로 계산한다.** DB 는 UTC 로 돈다. n8n 이 한국 시간 값을 직접 넣으면 잠금이 9시간 15분 걸린다.
- 잠그면 포털이 그 계정의 열린 세션도 다음 요청에서 바로 끊는다(따로 세션 종료를 안 해도 된다). 잠금 해제는 관리자 화면의 **잠금 해제** 단추.
- 허용되지 않은 열(`role`, `id` 등)은 조건(`WHERE`)에도 쓸 수 없다. 사용자는 `username` 으로 찾는다.
- n8n 이 바꾼 내용은 포털 보안 로그에 남지 않는다. 대응 이력은 n8n 실행 기록에 남긴다.

**장비 제한은 방화벽으로 한다(중요)**
- Docker Desktop 은 설치 때 자기 프로그램에 **모든 원격 주소 허용** 방화벽 규칙을 만든다. 그래서 DB 포트를 열면 같은 망의 누구나 닿고, "192.168.3.15 허용" 규칙을 더해도 효과가 없다. 대신 **"192.168.3.15 을 뺀 모든 주소 차단"** 규칙을 건다(차단이 허용보다 우선).
- MySQL 은 Docker 의 주소 변환 때문에 모든 접속을 Docker 게이트웨이(172.21.0.1)에서 온 것으로 본다. 그래서 계정을 `nexus_n8n@192.168.3.15` 로 만들면 아무도 접속할 수 없다. 계정 호스트는 `%` 이고, 장비 제한은 방화벽 규칙이 맡는다.
- 순서(이 PC, 관리자 권한 필요):
  1. 관리자 PowerShell 에서 `powershell -ExecutionPolicy Bypass -File scripts\n8n_db_firewall.ps1 -AllowIp 192.168.3.15`
  2. `.env` 에 `DB_BIND=0.0.0.0` 을 두고 `docker compose up -d` (컨테이너가 다시 만들어진다, 데이터는 그대로)
  3. n8n 장비에서 접속 확인, 다른 장비에서는 접속이 안 되는지 확인
- **적용 상태(2026-10-20):** 방화벽 차단 규칙 2개(11:47) → `.env` `DB_BIND=0.0.0.0` → 컨테이너가 `0.0.0.0:3307` 로 떠 있음. 이 PC 에서 `127.0.0.1`·`192.168.3.14` 두 경로로 `nexus_n8n` 접속·조회가 되고 `password_hash` 는 거부(1143), 연결은 기본으로 TLS(TLS_AES_256_GCM_SHA384). MySQL 은 두 경로 모두 `nexus_n8n@172.21.0.1` 로 본다(주소 변환). **192.168.3.15 에서의 실제 접속과 다른 장비에서의 차단은 아직 확인 전**(진혜정·이시헌 확인 필요). 컨테이너가 11:45 에 열린 주소로 다시 만들어지고 방화벽 규칙이 11:47 에 걸려, 약 2분 동안 DB 포트가 망 전체에 열려 있었다.
- n8n 장비가 바뀌면 1번을 새 IP 로 다시 실행한다. 포트를 다시 닫을 때는 `.env` 의 `DB_BIND` 를 지우거나 `127.0.0.1` 로 하고 `docker compose up -d`, 그다음 `-Remove` 로 규칙을 지운다.
- 계정을 다시 만들거나 비밀번호를 바꿀 때: `python scripts/create_n8n_account.py` (`--rotate` 는 새 비밀번호, n8n 자격 증명도 바꿔야 한다).


## 5. 공격 IP 차단 연동 (n8n 자동 대응)

포털은 DB의 locked_ips 테이블을 기반으로 접속자의 실제 클라이언트 IP를 실시간 검사하여 403 차단합니다.
n8n은 이상 징후나 공격(R1 브루트포스, R2 SQLi 등) 감지 시 DB 노드로 쿼리를 실행해 즉시 차단할 수 있습니다.

### n8n 이 쓰는 IP 차단 SQL

`sql
-- 특정 IP 30분간 자동 차단 (이미 있으면 만료 시각 연장)
INSERT INTO blocked_ips (ip_address, reason, blocked_until, created_by)
VALUES (?, 'R1_bruteforce', DATE_ADD(NOW(), INTERVAL 30 MINUTE), 'n8n')
ON DUPLICATE KEY UPDATE
    reason = VALUES(reason),
    blocked_until = VALUES(blocked_until),
    created_by = 'n8n';

-- 특정 IP 차단 즉시 해제
DELETE FROM blocked_ips WHERE ip_address = ?;

-- 현재 유효한 차단 목록 조회
SELECT ip_address, reason, blocked_until FROM blocked_ips WHERE blocked_until > NOW();
`

- 차단된 IP로 요청이 오면 포털은 즉시 403 Forbidden을 반환하며, 보안 로그에 event_type=ip_blocked, decision=BLOCK 이벤트가 기록됩니다.
- 관리자 화면(/admin/blocked-ips)에서도 현재 차단된 IP 목록을 확인하고 수동으로 차단/해제할 수 있습니다.
