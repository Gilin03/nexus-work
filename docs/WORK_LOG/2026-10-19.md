# NEXUS WORK 작업 기록 — 2026-10-19

## 오늘의 목표

`docs/SECURITY_LOG_SPEC.md`를 기준으로 Graylog 탐지 목표를 8개에서 12개로 확장하고, 현재 저장소 로그로 가능한 범위와 앱/AI Gateway 추가 작업을 구분했다. Graylog→n8n payload 계약과 n8n 담당자가 바로 쓸 수 있는 R1–R12 Mock Payload도 갱신했다.

이번 작업은 문서와 인터페이스 계약만 다뤘다. 앱 코드, Wazuh 설정, Graylog 실제 설정, n8n workflow는 변경하지 않았다.

## 추가 결정사항: 발표·운영 화면 단순화

실무형 요소를 최소 수준으로 반영하기 위해 Graylog Stream 3개(`NEXUS_AUTH`, `NEXUS_AI_SECURITY`, `NEXUS_WEB`)와 간단한 필드 정규화를 도입했으며, 발표·재현·테스트 가능성을 우선했다. Pipeline은 우선 `ts`를 Graylog timestamp로 맞추고, 이미 동일한 필드명으로 들어오는 값은 변환하지 않는다. 새 탐지 규칙이나 추가 Stream은 만들지 않았다.

Wazuh 범위는 uploads FIM으로 유지하고 결과를 `NEXUS_WEB`에서 확인하도록 정리했다. R1/R12처럼 순서 상관이 필요한 조건은 설치된 Graylog의 기능을 확인할 때까지 “기능 확인 필요” 상태를 유지한다.

## 새 규칙 R9–R12 목적

- **R9:** 일반 직원 계정의 관리자 전용 접근 거부를 찾는다. `/admin` 경로 텍스트만으로 판단하지 않고 `event_type=authz_deny`, `role`, `reason=insufficient_role`, `required=admin`을 주 조건으로 삼는다.
- **R10:** AI를 거치지 않은 직접 기밀 자원 접근 거부를 찾는다. 현재 `confidential_access`는 성공한 `ALLOW`만 기록하므로, 관리자/기밀 경로에 대한 `authz_deny`(`required=manager,admin`)와 범위 밖 급여 접근(`resource=payroll:<id>`)을 사용한다.
- **R11:** R3의 단발 DENY와 분리해 같은 session 또는 user가 5분 내 보호 Tool 호출을 3회 이상 거부당한 지속 시도를 찾는다.
- **R12:** 게시/첨부/문서를 AI가 읽은 뒤 보호 Tool을 호출하고 Security Gateway가 DENY한 공격 사슬을 상관한다. 간접 Prompt Injection 콘텐츠가 존재한다는 이유만으로 차단/경보하지 않는다.

## 현재 구현 가능/미구현 구분

저장소에는 `logs/security.jsonl` JSONL 로그와 로그인, `authz_deny`, `not_found`, `confidential_access`, `post_created`, `attachment_download` 등의 이벤트가 있다. 공통 필드는 `ts`, `event_type`, `user`, `role`, `src_ip`, `method`, `path`, `decision`, `reason`이다. `authz_deny`에는 경우에 따라 `required` 또는 `resource`가 추가된다.

Graylog, Wazuh, n8n 설정은 현재 저장소에서 확인되지 않았다. `request_id`, `session_id`, `injection_type`, `source_type`, `trigger_source`, `tool_name`, `resource_class` 및 AI Tool/콘텐츠 열람 이벤트도 아직 없다.

- **기존 로그 기반:** R5–R10. 실제 Graylog 수집·field mapping과 R5/R6/R8 집계 및 R7 시간 처리는 필요하다.
- **부분 가능:** R1의 account_locked 분기는 현재 이벤트로 가능하다. 실패 3회 후 성공 분기는 이벤트 순서 상관 기능 또는 앱 집계가 필요하다.
- **앱/Gateway 추가 필요:** R2 직접 인젝션 탐지, R3 Tool 권한 거부, R4 internal API 호출, R11 반복 Tool 거부.
- **R12:** 현재 로그만으로는 콘텐츠가 실제 AI에 읽혔는지, 그 읽기가 어떤 Tool 호출을 유발했는지 알 수 없다. 공통 ID·resource ID·AI 열람 이벤트 추가 후 구현 가능(B)으로 판단했다.

## 앱 담당자에게 요청할 로그

1. 직접 Prompt Injection은 AI Agent/Tool 전달 전에 차단하고 `prompt_injection_detected`, `injection_type=direct`, `decision=DENY`, `pattern_id`만 기록한다. Prompt 원문은 금지한다.
2. 보호 Tool 실행 직전에 Security Gateway가 사용자 권한을 재검사한다. 차단 시 `agent_tool_call` DENY와 `tool_name`, `resource_class`, `request_id`, 불투명 `session_id`, `trigger_source`를 기록한다.
3. R4는 `internal_api_call`에 `caller_service`, 실제 ingress `src_ip`, `path`, `decision`, `request_id`를 남긴다. 보호 전 ALLOW와 보호 후 DENY를 구분하고, 인증 토큰은 기록하지 않는다.
4. R11/R12를 위해 반복 Tool DENY와 `session_id`/`request_id` 전파를 추가한다. 게시/첨부/문서 식별자, AI가 실제로 읽은 콘텐츠 리소스(`ai_content_read` 또는 동등 이벤트), Tool 이벤트의 `trigger_resource_id`가 연결되어야 한다.
5. 현재 `suspicious_input`은 특정 필드 이름을 제외하면 탐지 값 앞부분을 기록할 수 있다. 대화/게시/첨부를 포함한 모든 입력에서 원문이 남지 않도록 앱 담당자가 점검한다.

## n8n 담당자에게 전달할 변경점

- Canonical payload 버전을 `1.1`로 올리고 root `action_level`을 추가했다. 값은 `observe`, `alert`, `contain`이며 권고값이다.
- `rule.stable_name`은 영문 분기 키, `rule.display_name`/`alert.title`은 한국어 사람용 표시명으로 분리했다.
- R1–R12 각 규칙에 대한 mock envelope를 명세에 추가했다. 집계 규칙은 `event.evidence`에 안전한 횟수와 시간창만 전달한다.
- alert ID를 idempotency key로 사용한다. Prompt/게시글/첨부 본문, 토큰, backlog는 금지한다.
- R4는 `event.decision`을 반드시 확인한다. ALLOW는 방어 전 성공 재현, DENY는 방어 후 차단 증거다. `action_level=contain`만 보고 이미 차단됐다고 기록하지 않는다.
- R2는 앱 차단 후 alert, R7은 observe부터 시작하는 권고로 정했다. 실제 workflow 대응은 n8n 담당자가 API 가능 범위와 중복 실행 방지를 포함해 별도로 결정한다.

## Wazuh/Graylog 담당 다음 작업

가장 먼저 팀 연결표에서 Graylog/Wazuh Manager 주소, 설치 버전/에디션, 입력 포트·프로토콜, 허용 IP를 확인한다. 앱 JSONL을 Wazuh localfile로 전달하는 기존 기획과 포털 GELF 12201 계획 중 앱 로그 수집 경로를 하나로 확정하고, Wazuh FIM Syslog JSON 5140 전달과 중복되지 않게 정리한다. 그다음 시험 로그 1건으로 `ts`가 Graylog timestamp로 파싱되는지, `required`/`resource`/AI 신규 필드가 검색되는지, R1/R12에 필요한 Event Correlation 기능을 사용할 수 있는지 확인한다.

Graylog 접속 정보/정상 Docker·Proxy 출발지 allowlist가 확정되기 전에는 임의 IP를 문서에 넣거나 R4를 활성화하지 않는다. n8n 담당자는 Graylog 연결을 기다리지 않고 본 명세의 mock payload로 webhook 수신과 R1–R12 분기를 먼저 개발할 수 있다.

### 변경 내용 및 파일/설정

- 앱 코드와 서비스 설정 변경 없음.
- Docker에서 Graylog 이미지 태그 `graylog/graylog:6.1`, Wazuh Manager `wazuh/wazuh-manager:4.9.0`, n8n 컨테이너의 실행 상태를 확인했다.
- Wazuh Manager CLI 버전은 `v4.9.0`; Windows Wazuh Agent `board-host`(ID `001`, Windows 11, v4.9.0)는 `Active`였다. WSL2 Agent ID `003`도 활성 상태였다.
- Graylog load balancer 상태 확인은 HTTP 200이었다. 인증이 필요한 Graylog system/input API는 HTTP 401을 반환해 입력 목록과 활성 상태는 확인하지 못했다. Docker 공개 포트는 Graylog UDP `1514`, GELF TCP/UDP `12201`; 문서의 `5140`은 현재 공개 매핑에 없었다.
- 포털은 Windows 호스트 `http://127.0.0.1:5070`에서 HTTP 200으로 실행 중이다. 앱 설정의 기본 업로드 경로는 `C:\ktb\project_nexus_work\nexus-work\instance\uploads`이며 점검 당시 폴더는 없었다. `.env`와 현재 셸에서 `UPLOAD_DIR` override는 확인되지 않았다.
- `logs/security.jsonl`은 21개 유효 JSONL 레코드였고, 확인된 이벤트는 `authz_deny`, `chat_message`, `chat_reply`, `confidential_access`, `login_success`, `logout`, `not_found`, `server_error`였다. `request_id`, `session_id`, `severity`, `source_component`는 표본 로그에서 확인되지 않았다.
- Docker 네트워크에서 Graylog는 `172.18.0.7`, Wazuh Manager는 `172.18.0.3`이었다. n8n은 별도 bridge 네트워크의 `172.17.0.2`; MySQL은 `172.23.0.2`였다.

### 테스트 방법 및 결과

- Docker 컨테이너 상태 및 포트: `docker ps` / Docker 네트워크 검사 — Graylog, Wazuh, n8n 실행 확인.
- Graylog health endpoint — HTTP 200. 인증 API — HTTP 401이므로 input 존재 여부 미확인.
- n8n `/healthz` — HTTP 200.
- 포털 `127.0.0.1:5070` — HTTP 200, 응답 Server 헤더 `NEXUS`.
- Manager `agent_control -i 001` — Agent `Active`.
- `security.jsonl` 파싱 — 21줄 중 유효 JSON 21줄, 오류 0줄.

### 문제와 해결

- 5140은 실제 Docker 공개 포트가 아니며 Graylog input 상태는 인증 부족으로 확인되지 않았다. 포트를 추측해 변경하지 않고 3단계에서 현재 input/프로토콜을 먼저 확인하기로 했다.
- Graylog 이미지 태그 수준은 확인했으나 컨테이너 내부 API 인증이 없어 정확한 patch 버전은 미확인이다.

### 남은 작업 및 전달

- 3단계에서 Graylog 입력의 실제 프로토콜/포트를 확인한 뒤 Wazuh Manager 전송을 맞춘다. UDP 1514가 보인다는 사실만으로 Syslog input이 활성이라고 가정하지 않는다.

## 실제 구현 2단계 — uploads Wazuh FIM

### 작업 목적

포털의 기본 uploads 폴더에 대해서만 Wazuh FIM을 구성하고 생성·수정·삭제 탐지 여부를 확인한다. DB 문서는 대상에 포함하지 않는다.

### 변경 내용 및 파일/설정

- 대상 경로가 없어서 `C:\ktb\project_nexus_work\nexus-work\instance\uploads` 폴더를 생성했다.
- Windows Agent 001의 `C:\Program Files (x86)\ossec-agent\ossec.conf` 기존 `<syscheck>` 안에 다음 항목 하나를 추가했다: `<directories check_all="yes" realtime="yes">C:\ktb\project_nexus_work\nexus-work\instance\uploads</directories>`.
- 변경 전 설정 백업: `C:\Program Files (x86)\ossec-agent\ossec.conf.codex-backup-20261019`.
- Wazuh Agent 서비스를 재시작했다. 기존 syscheck 경로와 DB 설정은 변경하지 않았다. 앱 코드, Graylog, Wazuh Manager, n8n 설정 변경은 없었다.

### 테스트 명령/방법 및 결과

- 설정 XML 파싱 및 업로드 경로 항목 수 확인 — XML 유효, `realtime=yes`, `check_all=yes`, 경로 항목 1개.
- Agent 로그 확인 — uploads 경로가 `size`, 권한, 소유자, 시간, 해시, `realtime` 옵션으로 감시 등록됨.
- 고유 시험 파일 `codex-fim-verification-20261019.txt`를 생성·수정·삭제하고 Manager `/var/ossec/logs/alerts/alerts.json`에서 해당 경로를 검색했다.
- 생성 — Wazuh rule `554` (`File added to the system.`) 확인.
- 수정 — Wazuh rule `550` (`Integrity checksum changed.`) 확인.
- 삭제 — Wazuh rule `553` (`File deleted.`) 확인.
- 시험 파일은 테스트 후 삭제되어 uploads 경로에 남아 있지 않다.
- Agent 001은 재시작 후 `Active`, 서비스는 `Running`이었다.

### 문제와 해결

- 설정 파일이 관리자/SYSTEM 전용이라 현재 로그인 계정으로는 쓰기 권한이 없었다. 권한 상승 후 백업을 만들고 필요한 한 항목만 추가했으며 Agent 재시작과 설정 검증을 마쳤다.
- 초기 시험 조회 시 Manager alerts에 항목이 아직 도착하지 않아 Agent FIM 상태와 manager 로그를 확인한 뒤 수 초 내 재조회했다. 최종적으로 생성·수정·삭제 3종 모두 Manager alert로 확인했다.
- 테스트 시각대 Manager `ossec.log`에서 `Too many fields for JSON decoder` 오류가 관찰됐다. FIM 세 이벤트는 각각 정상 rule로 기록되어 이번 FIM 검증은 통과했지만, 오류의 원인은 아직 분리·확인되지 않았다.

## 실제 구현 4단계 — 앱 → Graylog GELF

### 작업 목적

기존 `security.jsonl` 기록을 유지하면서 포털의 보안 이벤트를 기존 Graylog GELF UDP 입력으로 전달한다. Prompt·비밀번호·토큰 등 민감 원문은 Graylog로 보내지 않고, 시험 이벤트에서 실제 저장 필드와 timestamp 변환을 확인한다.

### 변경 내용 및 파일/설정

- `app/security.py`에 GELF UDP logging handler를 추가했다. GELF 1.1 JSON을 gzip 압축해 UDP로 전송하며, Graylog 장애/소켓 오류가 포털 요청 실패로 이어지지 않도록 전송 실패를 best-effort 처리한다.
- Graylog에는 허용 필드 목록만 보낸다. `prompt`, `body`, `message`, 비밀번호, 토큰, `value` 등 임의 필드/본문은 GELF payload에 포함하지 않는다. `reason`은 안전한 코드형 문자열에 한해 전송한다.
- 기존 JSONL에는 공통 필드 `source_component=portal`, `severity`를 추가했다. severity는 이벤트에 허용된 값이 명시되면 사용하고, 아니면 decision에서 info/low/medium/high로 기본 분류한다. 기존 `ts`는 JSONL에 유지하고 GELF reserved `timestamp`로 ISO 시각을 변환한다.
- 의심 입력 중 필드명이 prompt, content, document, attachment 등인 경우 탐지 종류만 남기고 입력 원문은 JSONL에도 남기지 않도록 `NO_VALUE_FIELDS`를 보강했다.
- `app/config.py`, `app/__init__.py`에 `GRAYLOG_GELF_ENABLED`, `GRAYLOG_GELF_HOST`, `GRAYLOG_GELF_PORT`를 연결했다. 실제 `.env`에는 활성화, `127.0.0.1:12201/UDP`를 설정했고 `.env.example`에는 테스트 기본 비활성 예시를 추가했다. 비밀값은 읽거나 변경하지 않았다.
- 테스트 격리를 위해 `tests/conftest.py`에서는 GELF 전송을 끈다. `tests/test_graylog_logging.py`에 로컬 UDP receiver를 사용한 전송·압축·필드 허용목록 검증을 추가했다.
- Wazuh Agent의 현재 `<localfile>` 목록을 다시 확인했다. `C:\ktb\project_nexus_work\nexus-work\logs\security.jsonl`은 수집 대상으로 등록되지 않았으며, 다른 실습 경로의 기존 로그 수집 설정은 변경하지 않았다. 따라서 현재 security.jsonl 이벤트에 Wazuh localfile과 GELF를 동시에 연결하지 않았다.

### 기존 로그 구조 및 테스트 방법/결과

- `logs/security.jsonl`의 기존 10개 `authz_deny` 표본과 Graylog 색인 표본은 모두 `reason=not_logged_in`, `role=-`이며 `required`가 없었다. 이는 로그인 역할 검사가 아닌 익명 요청 거부다.

- Graylog 6.1.16 Event Definition 검증 API는 신규 정의의 ID가 비어 있을 때 내부 Mongo 조회에서 `hexString can not be null` HTTP 500을 반환했다. 임시 비저장 24-hex ID를 검증 요청에 넣자 validation이 통과했다. 서버 로그와 Graylog 6.1.16 소스의 검증 경로를 확인했으며 저장소/서버 코드는 변경하지 않았다.
- 생성 API에 구형 문서에서 보이는 `entity` wrapper를 보낸 요청은 HTTP 400으로 거부됐고 어떠한 정의도 저장하지 않았다. 실제 실행 서버가 반환한 오류의 허용 필드에 따라 DTO 원문 형식으로 다시 생성해 HTTP 200을 확인했다.
- 양성: `role=employee` 및 `role=manager`의 안전한 app-shaped GELF `authz_deny` 이벤트를 NEXUS_WEB으로 전송했다. 둘 다 OpenSearch 원본에 `required=admin`으로 저장되고 R9 Event가 각각 생성됨 — **통과**.
- 음성: `role=admin`인 동일 구조의 `authz_deny` 시험 이벤트는 NEXUS_WEB 원본 검색에 나타났지만 R9 Event에는 생성되지 않음 — **통과**.
- Event search 결과에서 R9 양성 Event는 `user`/`path` 필드와 함께 확인했고, 음성 사용자 Event는 확인되지 않았다. 테스트는 synthetic app-shaped GELF이므로 운영 사용자가 실제로 발생시킨 거부 로그라고 보고하지 않는다.

### 문제와 해결

- 명세의 `employee/non-admin`을 저장소 실제 역할 집합 `employee`, `manager`, `admin`에 맞춰 비관리자 두 역할로 구현했다. 기존 이벤트 타입·사유·required 조건은 그대로 유지했다.

## 실제 구현 7단계 — R7 심야 로그인 성공

### 작업 목적

### 변경 내용 및 파일/설정

- Graylog Event Definition `[NEXUS][R7] 심야 로그인 성공` 생성 및 활성화 — ID `6ad590929d0f6c101daf8edf`.

- 하루 중 동일 로그인 사용자가 반복 Event를 만들지 않도록 Cron은 `0 5 5 ? * *`, timezone `Asia/Seoul`(매일 05:05 KST)로 설정했다. 검색 창은 6시간이며, 00:00부터 05:00까지의 이벤트를 포함한다.
- Graylog Event priority는 R7 계획의 observe에 맞춰 1로 설정했다. 필드/그룹 키는 `user`, `src_ip`; n8n Notification은 추가하지 않았다.
- 저장소에서는 `docs/WORK_LOG/2026-10-19.md`만 수정했다. 앱 코드, 기존 Stream, 기존 Event Definition은 수정하지 않았다.

### 기존 로그 구조 및 테스트 방법/결과

- 기존 `logs/security.jsonl`의 `login_success.ts`는 UTC ISO-8601이고 `event_type`, `user`, `role`, `src_ip`를 제공한다. 5070 재시작 전 성공 로그는 Graylog에 없어서, 비민감 synthetic GELF 시험 메시지로 시간 경계를 보완했다.
- Graylog 검색 API에서 KST 시작 `2026-10-18T15:00:00.000Z`(00:00 KST)와 종료 직전 `2026-10-18T19:59:59.999Z`(04:59:59.999 KST)는 매칭됐다. 종료 시각 `2026-10-18T20:00:00.000Z`(05:00 KST)와 종료 직후 `20:00:00.001Z`는 색인됐지만 규칙 검색 결과에서 제외됐다.
- Graylog Event Definition 비저장 검증 API — HTTP 200, `failed=false`. Cron validator도 `0 5 5 ? * *`를 `at 05:05`로 승인했다.
- 양성: 00:30 KST synthetic `login_success`만 포함하는 timerange로 Event Definition 수동 실행 — HTTP 204. 이벤트 검색에서 R7 정의 ID의 Event 1건과 `user=r7_positive_probe`, `src_ip=192.0.2.71` 확인 — **통과**.
- 음성: 12:24 KST synthetic `login_success` timerange로 수동 실행 — HTTP 204. 실행 전후 R7 Event 수가 1건으로 유지되고 음성 사용자 Event가 생성되지 않음 — **통과**.
- R7은 검증 후 활성화했다. 최종 조회에서 `state=ENABLED`, Cron 활성, timezone `Asia/Seoul`, 매일 05:05 설정 확인.

### 문제와 해결

- 처음 사용한 `timestamp` 범위의 종료 괄호가 포함형 `]`여서 정확히 05:00 이벤트까지 매칭했다. R7 명세가 05:00 미만이므로 종료 괄호를 배타형 `}`로 바꾸고 시작·종료 직전·종료 경계·종료 직후 네 시각을 각각 확인했다.
- 날짜식을 `now-1d/d+15h` 형태로 두면 UTC 날짜 경계에 따라 KST 날짜 선택이 하루 밀릴 수 있다. KST 날짜 기준으로 먼저 9시간 이동하고 하루를 내림한 뒤 UTC 시작/종료 시각을 계산하는 `now+9h/d-9h`, `now+9h/d-4h`를 적용했다.
- Graylog 6.1.16의 읽기 응답 DTO에서 `tags`와 `tactics_techniques`를 그대로 복사하면 신규 정의 검증이 400으로 거부됐다. 생성/검증 DTO에서 읽기 전용 필드를 제거한 뒤 비저장 검증이 통과했다. 기존 정의에는 요청을 보내지 않았다.
- Event 생성 직후 1시간 범위 조회에서는 과거 시험 원본 시각 때문에 검색 결과가 보이지 않았다. 이벤트 검색 범위를 시험 원본 시각을 포함하는 24시간으로 넓혀 Event 1건을 확인했다. 탐지 실패가 아니라 검증 조회 범위 문제였다.

### 남은 작업 및 전달

- R7 구현 및 시간 경계·Event 양성/음성 검증 완료.
- 다음은 R8 404 경로 스캔이다. `not_found`의 실제 JSONL/GELF 필드와 Stream 분류부터 확인하고, 명세의 같은 `src_ip` 60초 내 30회 조건을 유지해 진행한다.
- 시험 이벤트는 `user=r7_*` synthetic 표식으로 식별 가능하며 운영 사용자 활동 증거로 해석하지 않는다.

## 실제 구현 7단계 — R8 404 경로 스캔

### 작업 목적

SECURITY_LOG_SPEC.md R8 조건인 같은 `src_ip`에서 60초 동안 `not_found`가 30회 이상인 경우를 `NEXUS_WEB`에서 탐지하고, 30회 양성 및 29회 음성 경계를 확인한다.

### 변경 내용 및 파일/설정

- Graylog Event Definition `[NEXUS][R8] 404 경로 스캔` 생성 및 활성화 — ID `6ad5911d9d0f6c101daf8ff2`.
- 입력 Stream `NEXUS_WEB`, query `event_type:not_found`, group-by `src_ip`, count `>29`(정수형 count의 `>=30`과 동치), `search_within_ms=60000`, `execute_every_ms=60000`으로 구성했다. 우선순위는 3이며 알림 Notification/n8n 연결은 추가하지 않았다.
- 이벤트 키와 검색 필드는 `src_ip` 중심으로 두었다. 입력 로그에는 `path`가 포함되지만 집계 Event의 `path` 필드 제공값은 빈 문자열로 확인됐다. `path`를 group-by에 추가하면 URL마다 집계가 쪼개져 R8 임계값이 무효화되므로 조건에 추가하지 않았다. 원본 Graylog 메시지에서 개별 경로를 확인할 수 있다.
- 저장소에서 `docs/WORK_LOG/2026-10-19.md`만 수정했다. 앱 코드, 기존 Stream 및 기존 Event Definition은 수정하지 않았다.

### 기존 로그 구조 및 테스트 방법/결과

- 기존 `logs/security.jsonl`에서 `not_found` 8건을 확인했다. 필드는 `ts`, `event_type`, `user`, `role`, `src_ip`, `method`, `path`, `decision`, `reason`으로 R8 조건에 필요한 이벤트 유형과 출발지 IP가 있다.
- Graylog 최근 7일 `event_type:not_found`는 3건, `src_ip` 누락 0건이었다. 그중 `NEXUS_WEB`에서 검색된 기존 이벤트는 1건이었다. 표본에 따라 Graylog `path` 필드 존재 여부가 다르지만 R8 탐지 조건은 이를 사용하지 않는다.
- 안전한 synthetic GELF 59건을 Graylog에 보내 Stream 라우팅과 집계를 검증했다. `NEXUS_WEB` 검색에서 양성 IP `198.51.100.88` 30건, 음성 IP `198.51.100.89` 29건이 각각 확인됐다. 두 시험 집합의 필드에는 `event_type`, `src_ip`, `path`가 있었다.
- 양성: 30건만 포함하는 약 2.322초 timerange로 Event Definition 수동 실행 — HTTP 204. 이벤트 검색 색인 반영 후 R8 Event 1건, key/field `src_ip=198.51.100.88` 확인 — **통과**.
- 음성: 29건만 포함하는 별도 timerange로 수동 실행 — HTTP 204. 이후 조회에서도 전체 Event 수는 1건이며 `198.51.100.89` Event는 없고 기존 양성 Event가 유지됨 — **통과**.
- 정의 검증 API는 `failed=false`로 통과했다. 최종 조회에서 `state=ENABLED`, 60초 탐색/실행 간격 및 count `>29` 조건을 확인했다.

### 문제와 해결

- 첫 수동 실행 직후 이벤트 검색에서는 결과 0건이었으나 같은 정의 ID로 재조회하자 Event 1건이 검색됐다. 원본 로그는 실행 전 이미 30건 색인돼 있었고, Event Definition `matched_at`도 실행 시각으로 갱신됐다. Event 검색 색인 반영 지연으로 판단해 Event 검색을 재조회했고 양성 Event를 확인한 뒤 음성 테스트를 진행했다.
- 집계 Event에서는 개별 `path` 값이 빈 문자열이었다. URL 경로를 group-by에 추가하면 같은 출발지의 30회 탐지 조건 자체가 분할되므로, 탐지 조건은 명세대로 `src_ip`와 count만 사용하고 원본 로그의 `path`를 조사 증거로 유지한다.

### 남은 작업 및 전달

- R8 구현 및 Stream 분류, 30/29 경계 양성·음성 검증 완료.
- 다음 순서는 R5 계정 스프레이이며, 현재 `login_failure` 로그의 `src_ip`, 서로 다른 `user`, 5분 시간 범위 및 distinct 집계 지원을 먼저 확인한다.
- 시험 로그는 예약된 문서용 주소 `198.51.100.88`, `198.51.100.89`와 `/r8-test/` 경로로 표시했다. 운영 공격 활동으로 해석하지 않는다.


## 실제 구현 7단계 — R5 계정 스프레이

### 작업 목적

SECURITY_LOG_SPEC.md의 R5 조건인 같은 `src_ip`에서 5분 안에 서로 다른 사용자 5명 이상의 `login_failure`가 발생한 경우를 `NEXUS_AUTH`에서 탐지하고, 5명/4명 경계를 검증한다.

### 변경 내용 및 파일/설정

- Graylog Event Definition `[NEXUS][R5] 계정 스프레이` — ID `6ad592729d0f6c101daf9264`를 생성하고 양성·음성 테스트 후 활성화했다.
- Stream `NEXUS_AUTH`, query `event_type:login_failure AND user:* AND NOT user:"-"`, `group_by=src_ip`, `card(user)>4`(고유 사용자 5명 이상), 5분 탐색 창(`300000ms`), 60초 실행 간격을 사용했다. Graylog priority는 3이며 n8n Notification은 연결하지 않았다.
- 앱 코드와 기존 Stream/Event Definition은 수정하지 않았다. 저장소 변경은 이 작업 기록만이다.

### 기존 로그 구조 및 테스트 방법/결과

- `logs/security.jsonl`의 `login_failure` 이벤트 구조와 Graylog `NEXUS_AUTH` 메시지를 확인했다. 기존 데이터에 R5 양성 집합이 없어 비민감 synthetic GELF 로그로 임계값 경계를 만들었다.
- 양성: 예약 문서용 IP `198.51.100.121`에서 `r5p-*` 5개 사용자로 5건을 전송했다. Graylog read-only 집계에서 `count=5`, `card(user)=5`를 확인했다. Event Definition 수동 실행은 HTTP 204였고, 절대 시간 검색에서 key `198.51.100.121`, 메시지 `card(user)=5.0`인 R5 Event를 확인했다 — **통과**.
- 음성: `198.51.100.122`에서 5회 시도 중 사용자 1명을 반복해 고유 사용자가 4명인 집합을 전송했다. 같은 집계에서 `count=5`, `card(user)=4`를 확인했다. 동일 R5 실행/검색 범위에서 이 IP의 Event는 생성되지 않았다 — **통과**.
- 설정 활성화 후 API 재조회에서 `state=ENABLED`, Stream, `card(user)>4`, 300초 창, 60초 간격을 확인했다.

### 문제와 해결

- Graylog 6.1.16에서 series type `cardinality`는 등록되지 않아 Event 실행이 HTTP 500으로 실패했다. 설치 버전의 집계 series 이름 `card`로 바꾸고 검증 및 실행을 다시 통과시켰다. [Graylog 6.1.16 Cardinality 구현](https://github.com/Graylog2/graylog2-server/blob/6.1.16/graylog2-server/src/main/java/org/graylog/plugins/views/search/searchtypes/pivot/series/Cardinality.java)
- 짧은 수동 timerange로 집계하면 Event timestamp가 5분 bucket 끝으로 찍혀 당시 시각보다 미래에 놓일 수 있다. 그래서 최근 24시간 조회에서는 생성 직후 Event가 빠져 보였다. 실제 양성 여부를 먼저 미래 시각까지 포함해 확인했고, 이후 원본 시험 로그를 포함하는 정확한 5분 범위로 다시 실행해 bucket 종료 시각이 현재가 되도록 맞춘 뒤 Event와 음성 부재를 확인했다. Graylog 6.1.16 집계 처리 코드는 range bucket 종료 시각을 Event timestamp로 사용한다. [Graylog 6.1.16 AggregationEventProcessor](https://github.com/Graylog2/graylog2-server/blob/6.1.16/graylog2-server/src/main/java/org/graylog/events/processor/aggregation/AggregationEventProcessor.java)

### 남은 작업 및 전달

- R5 구현, 집계 및 positive/negative 검증 완료. R2/R3/R4/R11/R12는 실제 AI/Gateway 이벤트가 준비될 때까지 미구현 상태다.
- 다음 순서는 R6 잠금 후 로그인 재시도다. 기존 로그에서 `account_locked`, `login_locked`, 후속 `login_failure`의 필드/순서를 먼저 확인하고, Graylog 설치 버전이 동일 사용자·IP·시간 창 순서를 지원하는지 검증한다. 조건을 약화해 단순 실패 횟수 규칙으로 바꾸지 않는다.
- 시험 로그는 예약 문서용 IP `198.51.100.121`, `198.51.100.122` 및 `r5p-*`/`r5n-*` 사용자로 식별한다. 민감 원문이나 토큰은 기록하지 않았다.


## 실제 구현 7단계 — R6 잠금 후 로그인 재시도 (환경 기능 확인에서 중단)

### 작업 목적

SECURITY_LOG_SPEC.md의 R6 조건인 `account_locked` 발생 후 5분 안에 동일 `user`/`src_ip`에서 `login_locked` 또는 로그인 재시도가 발생한 순서를 Graylog가 정확히 탐지할 수 있는지 확인한다.

### 기존 로그 구조 및 환경 확인

- `app/auth.py`에서 계정 잠금 시 `event_type=account_locked`, `reason=max_failures`를 기록하고, 잠긴 계정으로 다시 로그인하면 `event_type=login_locked`, `reason=account_locked`를 기록하는 것을 확인했다. `app/security.py` 공통 로그에는 `user`, `src_ip`, `event_type`, `ts`가 포함된다.
- 현재 `logs/security.jsonl`에는 `account_locked=0`, `login_locked=0`, `login_failure=0`이며 `login_success` 1건만 있다. Graylog `NEXUS_AUTH` 최근 30일 집계에는 `login_failure=23`, `login_success=6`만 있어 R6 시험에 필요한 잠금/후속 재시도 이벤트가 실제로 수집된 적은 없다.
- Graylog 6.1.16의 `/api/system/plugins`는 플러그인 5개를 반환했고 목록에 Enterprise Correlation Engine 플러그인이 없었다. 저장된 Event Definition 유형도 기존 정의는 `aggregation-v1`이며, 읽기 전용 `/api/events/definitions/validate`에 `correlation-v1` 검증을 요청했을 때 HTTP 400 `Unable to map property type`로 거부됐다. R6 Event Definition은 저장하지 않았다.
- Graylog 공식 문서는 Event Correlation Engine을 Enterprise 기능으로 분류한다: [Graylog Correlation Engine](https://go2docs.graylog.org/1380099/interacting_with_your_log_data/correlation_engine.html).

### 문제 및 처리 결과

- R6는 선행 `account_locked`와 동일 사용자/IP의 후속 이벤트 순서를 5분 범위에서 확인해야 한다. 현재 설치된 `aggregation-v1`만으로는 그 이벤트 간 순서를 확인할 수 없고, `correlation-v1` 타입도 현재 런타임에서 사용할 수 없다.
- `login_locked` 단일 검색이나 실패 횟수 집계로 대체하면 명세의 선행 잠금·사용자/IP 일치·5분 순서 조건이 보장되지 않아 사용하지 않았다. R6 Event Definition 생성, positive/negative 시나리오, 활성화는 수행하지 않았다. 원인을 해결할 수 있는 Correlation Engine 기능이 현 설치에 없어 사용자 요청 순서에 따라 R1로 넘어가지 않았다.
- R6 확인 과정에서는 저장소 코드, 기존 Graylog 설정을 변경하지 않았다. 작업 기록 외에 파일 변경은 없다.

### 남은 작업 및 전달

- R6는 현재 환경에서 **미구현/차단** 상태다. Graylog Correlation Engine을 제공하는 Enterprise 라이선스/기능을 이 6.1.16 환경에 적용한 뒤 `correlation-v1` 검증을 다시 하고, `account_locked` → 같은 `user`/`src_ip` 후속 `login_locked` 양성 및 5분 밖/다른 사용자·IP 음성 시나리오를 검증해야 한다.
- R6가 해결될 때까지 순서상 다음인 R1(account_locked 단일 분기)은 진행하지 않았다. R2/R3/R4/R11/R12도 실제 AI/Gateway 이벤트 전이므로 미구현 상태를 유지한다.

## 실제 구현 — R6 앱 집계 이벤트 방식 적용 및 검증

> 위 “환경 기능 확인에서 중단” 기록은 Graylog 상관 기능 대체안을 승인받기 전의 상태다. 아래에서 앱 집계 방식으로 이어서 적용했으며 기존 기록은 당시 상황을 보존한다.

### 작업 목적

Graylog 6.1 Community에서 선행 이벤트 순서를 직접 상관할 수 없는 제약을 우회하되, R6의 원래 의미와 임계값을 유지한다. `account_locked` 이후 같은 user/src_ip의 다른 request_id 로그인 재시도 3회가 있을 때만 한 번 발생시킨다.

### 변경 내용 및 변경 파일/설정

- **Graylog 6.1 Community/현재 환경의 상관 기능 제약 때문에 앱 집계 이벤트 방식으로 대체**했다. 원본 `login_failure`, `account_locked`, `login_locked` 로그는 유지한다.
- `app/auth_events.py`를 추가해 MySQL `security_auth_events`에 최소 상관 상태를 기록한다. 잠금을 유발한 request_id는 제외하고, 같은 user/src_ip의 잠금 뒤 다른 request_id만 계산한다. `login_locked`는 후속 시도 1회로 세며 1–2회에는 파생 이벤트가 없다.
- 잠금 발생 시각부터 300초 이내 조건을 사용한다. 정확히 +300초는 포함하고 +301초는 제외한다. 세 번째 후속 요청에서만 `post_lock_retry_detected`를 만들며 `lock_request_id`의 상태 전이로 같은 잠금 구간에서 한 번만 emit한다.
- 각 HTTP 요청에 불투명 `request_id`를 부여하고, 파생 이벤트에는 `lock_request_id`, `trigger_event_type`, `count=3`, `window_seconds=300`만 추가한다. 비밀번호/토큰/프롬프트 입력값은 기록하지 않는다.

- 음성: 실패 2회 후 성공은 응답 `[401, 401, 303]`; 파생 로그 0건, Graylog R1 Event 0건을 확인했다.
- 테스트 계정과 해당 사용자의 `security_auth_events` 행 정리 완료. 비밀번호/API 토큰은 출력하거나 기록하지 않았다.

### 문제와 해결

- 초기 Event API 검색에서 `query=user:<test-user>` 필터가 기존 account_locked Event를 반환하지 않았다. 정의 ID만으로 Events API를 조회한 뒤 Event 필드의 user/event_type을 대조해 기존 Event가 정상 생성된 사실을 확인했다. 탐지 설정 변경은 하지 않았다.

### 남은 작업 및 다른 담당자 전달

- R1/R6 실제 앱 및 Graylog 분기 검증이 끝났다. 다음은 파생 이벤트와 login_locked의 `NEXUS_AUTH` 분류, 그 뒤 Event Definition을 해당 Stream으로 한정해도 되는지 안전성을 검토한다.

## 실환경 후속 검증 — NEXUS_AUTH Stream 분류

### 작업 목적

R1/R6 원본 및 파생 이벤트를 기존 `NEXUS_AUTH` Stream에서 검색할 수 있는지 확인한다.

### 변경 내용 및 변경 파일/설정

- Stream 수는 늘리지 않았다. 기존 `NEXUS_AUTH`의 활성 상태, OR 매칭, index set, 기존 규칙 3개는 유지했다.
- `event_type=account_compromise_suspected` (rule `6ad5af6b9d0f6c101dafde55`), `event_type=login_locked` (`6ad5af6b9d0f6c101dafde59`), `event_type=post_lock_retry_detected` (`6ad5af6b9d0f6c101dafde5d`)만 기존 Stream에 추가했다. `NEXUS_AUTH`, `NEXUS_AI_SECURITY`, `NEXUS_WEB` 세 Stream 이름은 그대로이며 그 외 Graylog 기본/시스템 Stream도 유지했다.

### 테스트 방법 및 결과

- 규칙 추가 뒤 새 전용 계정으로 실제 5070 R6/R1 흐름을 다시 수행했다. R6 5회 실패+잠금 후 5회 재시도에서 `account_locked=1`, `login_locked=5`, `post_lock_retry_detected=1`; R1 3회 실패 후 성공에서 `account_compromise_suspected=1`을 `NEXUS_AUTH` Stream 검색으로 각각 확인했다.
- 음성: 시험용 `agent_tool_call` GELF 한 건은 `NEXUS_AI_SECURITY`에서 1건, `NEXUS_AUTH`에서 0건으로 확인했다.
- Stream은 기존 구조를 보존하고 원하는 이벤트만 분류했다. 시험 계정과 MySQL 집계 상태 행은 정리했다.

### 문제와 해결

- Stream 규칙을 추가하기 전에 들어온 과거 메시지는 자동 재분류되지 않는다. 규칙 반영 후 실제 포털에서 새 이벤트를 발생시켜 분류를 검증했다. 설정 재생성이나 과거 메시지 이동은 하지 않았다.

### 남은 작업 및 다른 담당자 전달

- Stream 분류 positive/negative 검증을 마쳤다. 다음 단계에서 R1/R6 Event Definition의 `streams`를 `NEXUS_AUTH`로 제한해도 탐지가 유지되는지 확인한다. 실패하면 전역 검색 설정을 복원한다.

## 실환경 후속 검증 — R1/R6 Event Definition Stream 한정

### 작업 목적

전역 검색으로 동작하던 R1/R6 Event Definition을 `NEXUS_AUTH`에 한정해도 기존 조건과 탐지가 유지되는지 확인한다.

### 변경 내용 및 변경 파일/설정

- Graylog 6.1.16에서 두 Event Definition의 변경 전 전체 설정을 읽고, 변경 대상 `config.streams`만 `[6ad58a859d0f6c101daf8032]`로 지정했다. query, group_by, aggregation, priority, 스케줄, 알림은 변경하지 않았다.
- Graylog validation API가 두 설정 모두 `failed=false`를 반환한 뒤 업데이트했다. 업데이트 후 다른 config 항목이 변경되지 않았고 두 정의가 계속 ENABLED인지 확인했다.
- `docs/SECURITY_LOG_SPEC.md`에 NEXUS_AUTH 이벤트 유형과 R1/R6 Stream 범위를 반영했다.

### 테스트 방법 및 결과

- 정의를 Stream으로 한정한 뒤 GELF 시험 이벤트를 보냈다. R1 `account_compromise_suspected` positive Event `01M59BFHMTAM7Q91DKZKP7W6YG`, R1 원본 `account_locked` positive Event `01M59BFHMT6QST5BH050R1BQZD`, R6 `post_lock_retry_detected` positive Event `01M59BFQYF3EHDHAEHDFJ0D537`를 확인했다.
- 음성: NEXUS_AUTH 안의 `login_success`는 R1 Event를 만들지 않았고, `login_locked`는 R6 Event를 만들지 않았다. 각각 0건을 확인했다.
- 위 이벤트 원본 다섯 건이 `NEXUS_AUTH`에서 검색되는 것도 확인했다. 양성 3종과 음성 2종 모두 Stream 분류가 정상이다.

### 문제와 해결

- 변경 전/후 query와 집계 조건이 동일하고 Stream 내 positive/negative 결과가 정상이라 전역 검색으로 되돌리지 않았다. 기존 정상 탐지 범위를 유지하면서 탐색 범위만 NEXUS_AUTH로 좁혔다.

### 남은 작업 및 다른 담당자 전달

- R1/R6 실제 앱, Stream 분류, Stream 한정 Event Detection 검증 완료. 다음은 검증에서 확보한 allowlist 필드만 사용해 schema_version 1.1 R1/R6 payload 예시를 정리하고, AI/Gateway 이벤트 구현 준비 상태를 조사한다. n8n Webhook은 아직 연결하지 않았다.

## n8n 담당자 전달용 R1/R6 payload 예시

### 작업 목적

Mock이 아닌 실제 5070 인증 흐름에서 생성된 Graylog Event와 source message 값으로 n8n 담당자가 분기 검토에 쓸 schema_version 1.1 예시를 제공한다.

### 변경 내용 및 변경 파일/설정

- R6의 MySQL `lock_request_id` 증거는 비민감 opaque ID이며 n8n에 전달할 필요가 있어 `event.evidence` 허용 필드 목록에 추가했다.
- Graylog/N8n Webhook 설정은 변경하지 않았다.

### 테스트 방법 및 결과

- Graylog Events API와 메시지 검색 결과에서 R1 Event `01M59BBT2EHSY1VBST5MAM0H97`, account_locked Event `01M59BBT2EM7FBF6G6RTAJ82BS`, R6 Event `01M59BC38NS87B7SQQ65BFY5G4`의 ID, timestamp, priority, key, user/request ID, decision/reason/evidence를 교차 확인했다.
- 예시에 쓰인 source 메시지는 `NEXUS_AUTH` Stream에서 검색되는 실제 5070 앱 이벤트다. 테스트 계정은 정리했고 원문 비밀번호/토큰은 payload 예시나 작업 기록에 없다.

### 문제와 해결

- n8n Webhook URL/연결이 아직 준비되지 않았다. 따라서 예시는 실제 Graylog 데이터를 기반으로 구성했으며 실제 HTTP POST, n8n 분기, 중복 방지 저장을 확인했다고 주장하지 않는다.

### 남은 작업 및 다른 담당자 전달

- n8n 담당자는 예시 세 건을 R1 성공 후 의심, R1 잠금, R6 잠금 후 재시도 샘플로 받아 `rule.id` 분기와 `alert.id` idempotency 처리를 개발할 수 있다. 다음으로 R2/R3/R4/R11/R12 이벤트 emitter 준비 상태를 조사한다.

## 실환경 후속 검증 — AI/Gateway 이벤트 구현 준비도 점검

### 작업 목적

R1/R6 후속 검증 다음 단계로 R2/R3/R4/R11/R12에 필요한 현재 앱 코드, 로그 구조, 실행 중 서비스 및 문서 계약을 읽기 전용으로 확인해 구현 가능한 순서를 구분한다. 이번 단계에서는 AI/Gateway 기능과 규칙을 구현하지 않는다.

### 변경 내용 및 변경 파일/설정

- 코드와 실행 설정은 수정하지 않았다. 확인 대상은 `app/chat.py`, `app/security.py`, `app/auth.py`, `app/portal.py`, `app/messenger_api.py`, `app/__init__.py`, `app/config.py`, `db/schema.sql`, `docker-compose.yml`, `docs/SECURITY_LOG_SPEC.md` 및 실행 중인 컨테이너 목록이다.
- 앱 이벤트 호출부와 `GRAYLOG_FIELDS` allowlist를 확인했다. `request_id`는 공통 로그에 생성되고, `session_id`, `injection_type`, `source_type`, `trigger_source`, `tool_name`, `resource_class`, `resource_id`, `trigger_resource_id`, `pattern_id`, `caller_service`는 GELF 허용 목록에는 있지만 해당 AI/Gateway 이벤트를 생성하는 코드 호출부는 없다.
- `/chat/messages`는 존재하지만 기본 `CHAT_RESPONDER`가 사용자 입력을 되돌려주는 `placeholder_responder`다. 실제 AI 연결이나 Tool 실행 코드는 저장소에서 확인되지 않았다. 채팅 이벤트는 현재 `chat_message`, `chat_reply`, `chat_responder_error`이며 보안 로그에는 원문 대신 길이만 남긴다.
- 실행 컨테이너에는 Graylog, Wazuh, MySQL, n8n이 있으나 AI Gateway/Agent 전용 컨테이너는 보이지 않았다. 프로젝트 `docker-compose.yml`에는 MySQL만 정의되어 있다. 이 확인은 현재 컨테이너 목록과 저장소 파일에 한정된다.
- `.env`는 값을 열람하지 않고 키 이름만 확인했다. AI/LLM/Gateway 설정 키는 없고, `CHAT_RESPONDER` 설정도 코드 기본 placeholder 외에 확인되지 않았다.

### 규칙별 준비도 및 권장 순서

1. **R2 직접 Prompt Injection 차단 — 첫 구현 후보.** 기존 `/chat/messages`에서 응답기 호출 전에 검사·거부할 접점은 있다. 단, 탐지 pattern/category 기준과 false-positive 테스트 표본을 정한 뒤 `prompt_injection_detected` / `direct` / `DENY`를 원문 없이 기록해야 한다. 현재는 탐지기와 R2 이벤트가 구현된 상태가 아니다.
2. **R4 비정상 Internal API 호출 — 호출 주체 baseline 확인 후 후보.** Messenger JSON API와 토큰 인증 경로는 있으나 `internal_api_call`, `caller_service` 이벤트가 없고 정상 호출 IP/서비스 allowlist도 확인되지 않았다. 실제 정상 Docker/Proxy 호출 주소를 관찰·합의하기 전에는 탐지 기준을 활성화하지 않는다.
3. **R3 AI Tool 권한 위반 — 실제 Tool Gateway 다음.** 현재 앱은 responder 문자열 접점만 있고 보호 Tool 실행 경로, Tool별 사용자 권한 재검사, `agent_tool_call` DENY 생성기가 없다. Tool 실행 직전 Security Gateway 권한 검사를 담당하는 컴포넌트가 준비돼야 한다.
4. **R11 반복 AI Tool 권한 위반 — R3 이벤트 뒤.** R3 로그와 안정적인 session/user 키가 먼저 필요하다. 현재 Graylog Community 상관 기능 제약을 고려해, 임계값을 보존하는 집계 방식을 별도로 검토한 뒤 구현한다.
5. **R12 콘텐츠 기반 위험 Tool 호출 — 마지막.** `post_created`/첨부 관련 앱 이벤트는 일부 있지만 AI가 실제 읽은 콘텐츠를 나타내는 `ai_content_read`가 없고, `content_ingested`→읽기→Tool DENY를 잇는 `resource_id`, `trigger_resource_id`, request/session 연결도 구현되지 않았다. 전체 인과 흐름이 실제 ID로 검증되고 상관/집계 방식이 확인될 때까지 비활성 상태로 둔다. `prompt_injection_observed` 단독으로 R12를 만들지 않는다.

### 테스트 명령/방법 및 결과

- `rg`로 앱 코드와 문서에서 AI 이벤트 이름, route, `log_event` 호출, 필드 allowlist 및 R2/R3/R4/R11/R12 계약을 검색했다. 결과: 다섯 이벤트 및 `content_ingested`/`ai_content_read` emitter는 현재 없음.
- `app/chat.py` 및 `app/security.py`의 관련 범위를 읽어 실제 응답기 접점과 원문 비기록 동작을 확인했다.
- `docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Ports}}'`로 서비스 목록을 확인하고, `docker-compose.yml` 서비스 선언 및 `.env` 키 이름만 조회했다. AI/Gateway 전용 실행 서비스/설정은 확인되지 않았다. 비밀 값은 출력하지 않았다.
- 이 단계는 준비도 조사이므로 positive/negative 탐지 테스트 대상이 없고 실행하지 않았다. 애플리케이션 동작 및 Graylog 설정도 변경하지 않았다.

### 문제와 해결

- 기존 GELF allowlist에 미래 AI 필드가 있다는 사실만으로 emitter 또는 기능이 구현된 것으로 오해할 수 있다. 실제 `log_event` 호출부, chat responder 구현, 실행 컨테이너를 따로 확인해 준비 상태와 미구현 상태를 분리했다.

### 남은 작업 및 다른 담당자에게 전달할 내용

- 앱 담당자: R2의 직접 입력 탐지 pattern/category ID와 양성·음성 표본을 합의하고, 검사 위치를 `/chat/messages`의 responder 호출 전으로 둔다. 로그는 원문 없이 `request_id`, `session_id`, `injection_type=direct`, `pattern_id`, `decision=DENY`, `reason=direct_prompt_injection`를 제공한다.
- AI/Gateway 담당자: 보호 Tool 목록, 사용자 권한 재검사 계약, `agent_tool_call`의 DENY/ALLOW와 `tool_name`, `resource_class`, `trigger_source`, `trigger_resource_id`, request/session/resource ID 전파를 R3 전에 제공한다.
- 앱/인프라 담당자: R4 allowlist를 위해 정상 Messenger/API 호출의 실제 caller service 및 source IP를 확인해 전달한다. token 값은 로그/문서에 남기지 않는다.
- R11/R12는 각각 R3 이벤트/상관 키, 그리고 콘텐츠 입력·실제 AI 열람·Tool 거부 간 동일 ID 연결이 마련된 뒤 진행한다. R12의 10분 관계 조건은 낮추지 않는다.
- n8n Webhook 연결과 실행 이력은 아직 확인되지 않았다. 이전 단계의 R1/R6 payload는 실제 Graylog Event를 바탕으로 한 전달 예시이며 실제 Webhook delivery를 뜻하지 않는다.

## R2 직접 Prompt Injection 차단 구현 및 실환경 검증

### 작업 목적

`SECURITY_LOG_SPEC.md`의 R2 계약에 따라 `/chat/messages` 입력 경계에서 직접 Prompt Injection만 차단하고, 교육·설명 목적 문장은 정상 채팅으로 통과시키는지 앱과 현재 5070/Graylog 환경에서 확인했다. 차단된 입력은 채팅 DB, JSONL, GELF 어디에도 원문이 남지 않도록 했다.

### 변경 내용 및 변경 파일/설정

### 문제와 해결

- 초기 오탐 검토에서 정책 우회와 기밀 데이터 표현이 교육 문장 안에 함께 있는 경우를 탐지할 수 있었다. 조건을 문장 시작의 명령형으로 좁히고 동사 단어 경계를 추가했다. 새 음성 회귀 사례와 기존 positive 테스트가 모두 통과했다.
- 처음 시스템 Python으로 전체 테스트를 실행했을 때 `argon2`가 없어 수집에 실패했다. 저장소 `.venv` Python으로 다시 실행해 전체 476개 테스트가 통과했다.
- Event Definition의 이전 60초 검색 설정에서 초기 재현 이벤트가 중복 기록됐다. 설정을 15초 검색 창/15초 실행 간격으로 맞춘 뒤 최신 positive 세 건에서 pattern별 1건씩만 발생함을 확인했다. 이전 검증에서 생성된 Graylog 시험 이벤트는 이력 증거로 남아 있으며 삭제하지 않았다.

### 남은 작업 및 다른 담당자에게 전달할 내용

- R2 Flask 직접 입력 차단과 현재 Graylog 탐지는 완료됐다. n8n Webhook 전달/실행 이력은 이 단계에서 연결하거나 검증하지 않았다.
- AI Gateway가 나중에 연결되면 동일한 직접 입력 정책과 세 pattern ID를 유지해야 한다. Flask 세션 쿠키를 `session_id`로 재사용하거나 원문 prompt를 어떤 로그/저장소에도 기록하면 안 된다.
- 이번 R2 작업에서는 Ollama, Tool Gateway, 간접 인젝션 이벤트, R3/R4/R11/R12를 구현하거나 변경하지 않았다. 다음 단계 전까지 그대로 미구현 상태다.
- `/chat/messages` 경로는 있지만 responder는 현재 placeholder이고 실제 Ollama, Tool 실행기, Security Gateway는 아직 연결·구현되지 않았다. 다음 AI 작업은 Ollama 연결이다. R3 및 Tool 상관 기반 R11/R12는 Tool/Gateway와 권한 재검사가 준비된 뒤 진행하며, R4도 미구현이다.

## Graylog 6.1.16 R1/R2 priority 호환성 수정

Graylog 6.1.16의 priority enum은 1~3인데 R1/R2 정의가 4로 생성되어 Alerts 화면에서 `undefined.name` 렌더링 오류가 났다. 두 정의의 priority만 HIGH=3으로 바꾸고 query, Stream, schedule, group_by 등 나머지 DTO 설정은 유지했다. 명세의 관련 priority 설명과 R1/R2 HIGH 예시도 3으로 정정했다.

- 새 R1/R2 positive Event priority=3, 각 negative Event 0건, NEXUS_AUTH/NEXUS_AI_SECURITY 분류 및 R6 기존 positive/negative 탐지를 확인했다.
- 기존 priority=4 Event 19개(R1 8개, R2 11개)는 보존했다. 단건 삭제 API가 확인되지 않아 삭제나 저장소 직접 수정은 하지 않았다.
- Alerts는 최근 15분 범위에서 정상 렌더링됐다. 긴 기간 Events 검색은 `priority:[1 TO 3]` 조건으로 과거 레코드를 검색 결과에서 제외할 수 있음을 확인했다.
- 상세 원인, 조사 순서, API/UI 확인 및 재발 방지는 [Troubleshooting 기록](../TROUBLESHOOTING/2026-10-19-graylog-alerts-priority-ui-error.md)을 참조한다.
