# R3/R11/R12 Reliability Hardening Plan

> Implementation plan for the already-approved request. Keep R1/R2/R4/R5/R6/R7/R8/R9/R10, Wazuh, and pfSense unchanged.

**Goal:** Make AI Tool denial correlation durable, NEXUS ticket updates atomic under concurrent webhooks, Discord delivery resilient to rate limits, and AI provider Tool selection server-gated.

**Architecture:** Persist each R11 denial as a minimal row in the existing MySQL database, serialized by an advisory lock for the same user/session/tool. Move NEXUS alert ticket aggregates from workflow static data to atomic MySQL transaction-backed tables while preserving the existing ticket API and safe flags. Keep Discord credentials and delivery branches, adding failure-only retries. Add structured action selection for configured model providers; only server-validated allowlisted actions reach the existing Security Gateway.

**Tech Stack:** Flask, MySQL 8.4, n8n 2.37.7, Graylog 6.1.16, pytest.

## Global constraints

- Never persist raw prompt, attachment/document content, passwords, tokens, cookies, or credentials in security/ticket records.
- Keep `response_mode=dry-run`, `live_enabled=false`, and current `discord_enabled` state.
- Keep AI Tool execution server-side and re-check the authoritative role/permission immediately before protected reads.
- Do not alter existing rules R1/R2/R4/R5/R6/R7/R8/R9/R10, Wazuh, pfSense, or unrelated workflows.
- Preserve the existing working tree and do not stage, reset, checkout, commit, or push.

## Files and responsibilities

- `app/ai_tools.py`: persistent R11 grouping and guarded Tool dispatch.
- `app/ai.py`: provider-specific structured Tool selection.
- `db/schema.sql`, `db/grants.sql`, `db/migrations/20261022_ai_security_persistence.sql`: additive schema and least-privilege grants.
- `scripts/create_n8n_account.py`: scoped NEXUS incident-table privileges.
- `tests/support.py`, `tests/test_ai_tools.py`, `tests/test_ai.py`: cleanup and focused behavioral coverage.
- Published NEXUS n8n workflow: atomic Ticket transaction, DB-backed GET/actions, and failure-only Discord retry.

## Verification focus

1. Duplicate `request_id` must not increase R11 count or re-emit the third-denial marker.
2. Parallel denials for one key must serialize, while different session/tool keys remain independent.
3. A model response with malformed JSON, unknown action, or invalid arguments must never execute a Tool.
4. A valid model suggestion must still be denied for an unauthorized user before the confidential query.
5. Parallel identical alert IDs must count once; distinct rules for one source must all remain in the ticket.
6. Discord retries must not retry successful sends and must retain the existing credential/target.

## Execution

Implement and verify in this order: R11 persistence; structured provider Tool selection; MySQL Ticket persistence and n8n update; Discord retry; focused tests; one consolidated R3/R11/R12 live-path validation only if the current runtime and DB schema support it without weakening the safety flags.
